All seven steps of M6.6.2 are built (version 0.6.6.2). Its As built section lists the first six below; the rest were planned and are not in the code either. None is needed by a test yet.

RandomAccessFile

Refused in a sandbox (M9 and M10): its files are read and written whole or as streams, with no form of reading or writing at a position yet, so PagedFile and writeByteDiff cannot be tested in one.

Links

A sandbox has no symbolic links, so code that meets them cannot be tested in one.

Timed waits

A join or lock with a time limit takes real time; the sleeps of several threads add up on the sandbox's clock rather than overlapping.

Fonts

The planned folder of fonts kept with the tests is not in the repository: a sandbox sees the system's fonts unless given fontsFrom.

Cores

The number of cores has no sandbox form: availableProcessors() is the machine's.

@RealHost

Goes on a test or a class, not on a whole file (a file has no annotations).

@Timeout

Counts real time, not the sandbox's clock.

Faults: what

Faults can make list, read, write, open, delete, move, copy, mkdir and connect fail; not permissions, accept, send, or starting a program.

Faults: where

A fault names one path or every path: no patterns of paths; a connect fault names the host but not the port; none names a program.

Faults: when

Every time from when it is added, or after so many bytes or names; not "the nth time", nor after so much time.

Faults: how

Only an error with the system's message; a read or write that does part of its work, and a delay, are not built.

Reading back

A test cannot ask afterwards which faults fired or what a peer received; there is only files.changes(). (The planned before-and-after timing of step 1 was never written down either.)

Speed: leads, measurements and limits

BigInt and Complex speed

Left until after the emitter (the user, 2026-11-19: "we'll revisit bigint and complex speed after the emitter work"). Measured 2026-11-19 against Python's int (written in C): 3000! by multiplying in a loop 18 ms (Python 0.8), a 30,000-bit square 3.2 to 4.2 ms (0.13), a 60,000-bit by 30,000-bit division 8.2 ms (0.44), parsing 9,131 digits 2.0 ms (0.19), writing them 4.0 ms (8.6; Python's is quadratic). The digit loops run in the VM and its regions; each result is also copied once by frozen() (a BigInt can be a key). Leads, in the "Jade first" order: the VM's code for those loops, then a public C++ piece (the digit kernels) only if that falls short.

Two tests near GC stress's limit

Done 2026-11-19 with o-gc-quick: both split and given a quick mode; under GC stress their parts now take at most 35 s quick and 231 s full (native_sets_maps_keys.ww, the slowest left), far from the 600 s limit. native_split.ww's time was not its loops but making its 1M-item tables through a lambda, a collection at each (some 200 s a table): made by doubling now (40 ms), the same in both modes.

Found 2026-11-19 in 0.9.5025's runs: native_sets_maps.ww and native_split.ww went past the 600 s limit under GC stress in a full run, and passed when run again alone. Not from that commit: under GC stress, with the machine shared with a second full suite, they took 289 and 402 s on 0.9.5025 against 296 and 371 s on 0.9.5024, with the same output. So they sit within reach of the limit whenever the machine is busy. The remedy: less repeated work in them under GC stress, every distinct case still run once, as asked of the WebP session the same day about GC stress's time as a whole.

simulation

A path of field reads is one instruction only when it starts from a reference; from a plain read it made fields 18% slower, so it was left out.

Arithmetic

int / int, int % int and an int with a float in +, - and * are worked out at once in register code since M9 and M10's part zero (2a6d4d2), and a byte counts as an int in the quick ways. Still the general way: an int compared with a float, and an int divided by a float. (step 5)

Fixed 2026-11-10. Three times, under 24 tests at once, the runner itself failed, passing when the test was run again alone (jade_charts on 2026-11-09; infix.ww and override_required.ww [runner]: undefined variable 'compare' on 2026-11-10). The VM's fault, not the runner's: inside an inline extension's body a bare name is looked up on its receiver alone, which ImplicitFirst tells the lookup just after it, in members of the VM; a thread could give way between the two, at InvokeImplicit's safe point, and the next thread's bare name then read what it was told, looked on the wrong object and found nothing (or, without "alone", could have found a member of the same name there).

What ImplicitFirst gives is now kept with each thread's context when threads take turns, as a call's pending type arguments already were (saveContext, loadContext). tests/thread_bare_names.ww failed on every run before, without the stress setting.

points_values

The one benchmark the tail-call build runs slower than the other: 0.232 s with Clang against 0.167 with GCC on Linux (2026-11-10), as MSVC's switch was 25% faster on it on Windows. Likely an instruction whose hot part calls C++ (a call there gives the function a frame of its own, which the tail calls then pay on every pass) or one too large to stay in registers; to be found with the instruction counts and a profile.

Tensor expressions

Tensor arithmetic combined into one loop: (a * 0.5 + b).clamp(0.0, 1.0) run as one pass over the numbers rather than three, as numexpr and JAX do (M10-plan.html, left for later). Memory, not arithmetic, is the cost of each pass: the gradient by tensors is 205 ms for 3840 by 2160, the loop in C++ 8. The native code plan's loop templates are what it would be built on (native-plan.html).

Method calls

Small functions are put in place of their calls since 5c6f235 (a call cost about three times a small body); methods are not, a call of one costing about 17 ns, as a subclass may give it another body. A method of a value type, or of a class nothing extends, could be put in place the same way.

255 slots

A function that needs more than 255 slots keeps plain stack code.

Places

A line of execution has 3,072 places for values in variables; a frame for which none are left (deep recursion) keeps boxes. (step 6)

D171

A C++ function is given a small value in a box, except list.add.

D172

A field of an object made before its class's field types exist keeps a box.

MSVC

The MSVC build keeps the 8 address bytes threaded code puts before each instruction, but does not use them.

M13

Its first measurement, a heavy slice of the simulation ported and timed against the C++, was waiting on M6.5 to M6.7 and can be made now; it belongs to M13.

Standing cautions

  • Code placement (G65). Placement alone moves single benchmarks a few percent. Compare against a Clang build of the commit before, built the same way, count instructions where in doubt, and take differences under about 5% between builds of the same code as noise.
  • Stores and reads (part D). A 16-byte read of a value just written in two 8-byte stores waits: most of an R instruction's cost is how its result is stored and read. Writing every int and float result whole cost more than it saved.
  • Ref helpers (step 6). Any branch or call inlined into refClass or refBytes made reads of list items 75% slower, with identical run code: leave them as they are. The same goes for adding work to an instruction's hot part on Windows, where any call there gives it a frame.
  • Three ways of running. WW_REGISTER_CODE=joined and =plain are kept for testing and timing; the suite is to keep passing in all three.
  • One graphics card (M0). Jade's windows have been drawn only on this machine's NVIDIA card. Intel graphics, virtual machines and Remote Desktop, where OpenGL is weakest, are untried: the risk gui-plan.html's section 9 names, which a run on another machine would settle.

Left as they are, by decision

Not work: listed so that they are not taken up again by mistake.

  • G42 (and 8.6g): what a built program keeps for reflection is decided by types, so a # of any keeps every class's description. Costs size, never correctness; following values through the whole program was declined on 2026-11-03.
  • G63: start-up about 0.5 ms later, from reading the whole saved standard library.
  • G67: inside a generic class's method, a list made by an inline function from the class's type parameter is made without its type.
  • 8.3e: where one side of flag ? a : b is any or unit, the result is still the unchecked unknown type.
  • 8.8c: Windows has no setExecutable.
  • 8.9f: a grid cannot be a map key, and a part of a grid taken by ranges takes no step.
  • 8.9l: there is no flag for an opaque image; a ported RGB image is one filled with a solid colour.
  • The sandbox: the suite's own tests stay on the real system on purpose; there is no files.write (files are set up through FilePath), and the clock moves with Sandbox.advance(time).
