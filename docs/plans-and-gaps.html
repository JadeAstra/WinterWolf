From m0-findings.md

M0: what the two spikes found

M0 was two throwaway prototypes, built to test the riskiest designs in the plan before committing to them: the parser changes for Kotlin-style lambdas, and an OpenGL window with a text engine of our own. Both work. This is what was built, what it showed, and what it changes in the plan.

M0 was accepted on 2026-10-12, and the changes it suggested are now in the plan.

The code is on the branch m0-spikes, and the file paths below are in that branch. It is prototype code: it proves the designs and is not the form the features will finally take.

Spike 1: lambda literals, trailing lambdas, receiver blocks

What was built

In the real lexer, parser, compiler and VM:

  • { a, b -> ... } and { ... it ... } lambda literals, whose value is their last expression.
  • A lambda with no parameter list accepts no argument or one.
  • {} as the empty lambda and {:} as the empty map.
  • Trailing lambdas: button("OK") { ... }, grid { ... }, items.filter { ... }.
  • Blocks that run on an object, so that grid { hgap = 8; row { cell(...) } } works, with with(obj) { }, apply, also, let and run.
  • Type annotations with type arguments and function types: list<int>, map<string, list<int>>, (int) -> int, Grid.() -> Unit.

Three scripts exercise it, each passing from source, from a compiled .wwc and as a built executable, and under the sanitizer with collection stress: spikes/m0/lambdas.ww, spikes/m0/receivers.ww, and a table of corner cases, spikes/m0/grammar_probes.ps1. receivers.ww ends with the layout block from the examples' Launcher.kt, written as it would be ported, running against stand-in classes.

The existing test suite passes 94 of 94 with these changes in place.

The grammar conflicts, and how each was settled

ConflictOutcome
if ready() { ... }: body, or a lambda passed to ready()?In the condition of if, while and for a { always opens the body. Parentheses switch that off for what they enclose, so if (items.any { it > 1 }) { ... } works. This is Swift's rule. No existing test needed changing.
if items.any { it > 1 } { ... }, written without the parenthesesWas silently misread: the first block became the body. It is now a compile error at the second { that says to put the condition in parentheses.
{ starting a map or a lambdaA key followed by : is a map; names followed by -> on the first line are a lambda's parameters; {:} is the empty map; anything else is a lambda. Map keys were already restricted to a name, a string, a number or [expr], so one or two tokens of lookahead decide it.
{ ready() ? it : 0 }, a ternary inside a lambdaReads correctly as a lambda.
{ x : int -> x * 2 }, a typed parameter that looks like a map entryReads correctly: the -> on the first line wins.
A { on the line after a callStarts a block, as today. A trailing lambda has to begin on the line the call ends on, as in Kotlin.
map<string, list<int>> ending in >>The parser splits the shift token.

The whole change to existing WinterWolf code was seven empty-map literals, two of them in the old gui library.

Things the plan did not have

  1. A parameter with a default before one without. Kotlin's grid(id: String? = null, build: JadeGrid.() -> Unit) is an error in WinterWolf today, where defaults must come last. The spike allows it. Such a parameter is filled by a lambda after the call or by name, and a call that leaves it without a value is an error.
  2. A trailing lambda goes to the last parameter, whatever came before it, including named arguments: spinner(3, min = 0, max = 20) { ... } is in Launcher.kt. Only the function being called knows where its last parameter is, so this is settled at the call.
  3. A top-level variable is not a local. In a receiver block, a variable of the enclosing function wins over a member of the object, as in Kotlin, but a global does not. A Kotlin fun main() { val children = ...; grid { ... children ... } } relies on the first. Ported as a fun main() it behaves the same; with its body moved to the top level of a script it would not, if the object happened to have a member of that name.
  4. A lambda's parameter list has to fit on its first line in the spike. Kotlin allows it to wrap. Decided: WinterWolf allows it too, in M1.
  5. Destructuring parameters, { (a, b) -> ... }, come with the destructuring feature and are not in the spike.

What it costs at run time

A name inside a lambda that is not one of its variables may belong to the object the lambda runs on, which is known only when it runs. Measured over two million iterations:

AccessTime each
A global from an ordinary function21 ns
The same from a lambda running on nothing25 ns
The same from a lambda running on an object that lacks the name34 ns
A field of the object by its bare name33 ns
The same field as this.total in a method28 ns
A method of the object by its bare name111 ns
The same as this.bump() in a method42 ns

So a bare name costs a few nanoseconds more than a resolved one, which is negligible for layout code. Calling a method by its bare name is the exception, at about two and a half times the cost: the spike builds a bound-method object for every such call. M1 gives it an instruction of its own.

Not done in the spike, for M1

  • The agreed rule for return in a lambda (D7). Today a return there leaves only the lambda.
  • The scope functions expanded in place by the compiler. Here they are ordinary calls.
  • Calling a receiver-typed parameter as g.build(). The spike's library code writes g.apply(build), which is also valid Kotlin.
  • A fast path for trailing lambdas, which now go through the named-argument call.
  • A proper error object for a missing argument; the spike throws text.

The two namespace questions

These concern how files are loaded once a folder is a namespace. They cannot be tested until namespaces exist. Both recommendations were accepted:

  1. Importing a folder loads every .ww file directly in it, once, as one unit, so that its files see each other whatever order they are in. This is what a Kotlin package is, and it is what import "jade" has to mean.
  2. Importing a file loads that file only, into the namespace of the folder it is in. A script with import "helpers" beside it therefore shares names with helpers.ww exactly as today, and the other scripts in that folder are not touched.

Spike 2: an OpenGL window and a text engine of our own

What was built

About 1,500 lines of C++ in src/spike, with no third-party code:

  • font.cpp: reads TrueType fonts and collections, maps characters to glyphs, measures by the one rule, rasterises outlines with exact-area antialiasing, and hints with a rule of our own (baseline, x-height and capital height snapped to whole pixels).
  • glwin.cpp: a Win32 window with an OpenGL 3.3 core context; the 28 OpenGL functions it needs fetched by name; one shader that draws fills, rounded rectangles, ellipses, lines and glyphs with smoothed edges; a glyph atlas; drawing into an offscreen framebuffer and reading it back; raw events delivered to a script function.
  • png.cpp: writes a PNG, for the pictures below.

It is reachable from scripts as a class Spike, used by spikes/m0/window.ww and spikes/m0/text_compare.ww.

Text: the part to prove

Running text_compare.ww draws Segoe UI at 11 to 28 pixels, our engine beside Windows' own, into spikes/m0/out (text_compare.png, text_compare_dark.png, and text_compare_zoom.png for the 12 and 13 pixel rows at three times the size). The pictures are not kept in the repository; the script makes them again.

  • It reads and draws correctly at every size tried, composite glyphs included.
  • Against Windows' greyscale rendering it is the more even of the two. Windows' is visibly irregular at 13 to 16 pixels (some letters and all the digits come out heavier).
  • Against ClearType it is slightly lighter at 11 and 12 pixels and otherwise close. A small darkening of thin strokes is the obvious adjustment; the engine has a setting for it.
  • Our hinting rule makes little visible difference at these sizes. It is cheap and stays, but the quality comes from the rasteriser, not from the hinting.
  • Measured widths equal Windows' exactly from 13 pixels up (573, 605, 688, 859 and 1,216 pixels for the test line). At 11 and 12 Windows' are wider (497 against 472, 517 against 515), because at small sizes it uses adjusted widths of its own. Ours are the font's.
  • Measuring and drawing agree. In the test scene each line has a rule drawn under it at its measured width, and at 1x every rule ends where the text ends.

One problem found, at HiDPI. The rule gives every character a whole number of logical pixels. At 2x the glyphs are drawn at twice the size but still placed on that grid, so spacing is a little loose and the measured width runs slightly past the text. The rule needs a clause for scaled displays: round each width in device pixels and report the total in logical ones. To settle at the start of M4.

Every font on this machine. Of the 486 font files in C:\Windows\Fonts, 463 are read and rasterised without error, also under the sanitizer. The other 23 are the two cases the plan already has for M4: 13 use the second outline format, and 10 are symbol fonts (Wingdings and the like) with a character map of their own.

The window

  • An OpenGL 3.3 core context on a plain Win32 window works with no library (tested on an NVIDIA card).
  • The scene is drawn into an offscreen framebuffer and read back from a window that is never shown, at 1x and 2x: scene.png and scene_2x.png. That is the hidden mode tests need.
  • Shapes are smooth at any angle and one-pixel rules are crisp.
  • Raw events reach the script: a second script shows the window, posts mouse, key and character messages to it, and the script counts them and quits on Escape.

Not tested

  • Any graphics driver other than this machine's. Intel graphics, virtual machines and Remote Desktop are the cases the plan's risk list names.
  • The window redrawing while it is being resized. The code draws from inside the resize message, but nobody has dragged its edge.
  • Per-monitor DPI. The spike process is not DPI-aware, so Windows would stretch it.
  • More than one window, and sharing textures between contexts.

Choices to confirm

D162The type of items.itemType (part 1)

Part 1 built a new built-in type, Type, for a type as the program runs. Since 2026-10-24 that is a Class (D48), one thing for one thing: items.itemType, map.keyType, map.valueType, values.itemType, a class's typeArguments, a field's and a parameter's type and a method's result give a Class (any# for a collection made without its type). So items.itemType == int#, and .name and isInstance work on each. Type is the standard library's own; written elsewhere it is an error saying to use a Class.

Decided2026-11-03: Already decided: D162, 2026-10-24 (a Class, not a Type); the text above is brought up to date.

D163How the C++ functions' results are checked (part 1)

By a test setting, not on every call. WW_CHECK_NATIVE_RESULTS=1 compiles a check after every call of an external function against its declaration (the standard library compiled from its source, the cache kept apart); the suite passes with it, and each checkpoint runs it beside the GC and thread stress settings. The C++ is fixed code, so the suite proves its declarations once, and later parts can then trust them while the program runs. The other way, a check on every call, costs every call of the C++. A list or map a C++ function gives is tagged at the call with the type the checker worked out, where it has none.

Decided2026-11-03: Confirmed, with a change: the stress settings (native results, GC, threads, copied reads) go into tests/run.ps1, so that each checkpoint runs them from the repo and not from a scratch script (done 2026-11-04, 4386343).

D164What the check changed in the standard library (part 1)

  • The coerce functions give one of their numbers as it was, so float.coerceIn(Number, Number) and the like say Number, with forms for all ints and all floats that say int and float. (2.5.coerceIn(0, 1) is the int 1.) This is the rule Math.min and Math.max follow too: ints and floats mixed give a Number.
  • A type parameter that the object a call is made on says nothing of (a Map written without type arguments) is unknown, not taken from the arguments: data.get(key, "missing") is no longer typed string? there.
  • Deck.toList (Deque until D183) builds a List<T> rather than casting its List<T?>, and Set == gives false for a set of other things rather than failing at a cast, now that casts are checked in full.
Decided2026-11-03: Confirmed as built (the text above is brought up to date).

D165The rules of a value type, as built (part 2)

  • value Point(val x : int, val y : int) needs a header whose entries are all fields. It is a data class: printing, ==, copy, coming apart.
  • It may implement interfaces, extends no class, and no class extends it.
  • A val field is given its value in the header, where it is declared in the body (one declared there with none is an error), or in the type's init; never again. Since part 4 a var field may be changed, but only through a place that holds the value, or in a mutating fun (D167); elsewhere p.x = 4 is a compile error saying to make a changed copy.
  • === on a value type is a compile error, as a value has no identity; through any it compares contents.
  • A value type cannot hold itself except where that field may be null; the checker reports it.
  • A value is copied wherever it is kept, so no two places share one. Which core may read or change a value in a list is D170's.
Decided2026-11-03: Confirmed as built (the text above is brought up to date with D167).

D179Jade's geometry as value types: decided (part 7)

You chose on 2026-10-19 to make Jade's Point, Dimension, Insets and Rectangle value types, and Jade's Sizes with them: a component's bounds and the sizes it keeps are inside it, and setSize, translate, setLocation, grow and setBounds are mutating methods. Nothing in Jade relied on sharing one; one val that was translated became a var. Since part 8 (group 9) they are the standard library's Point, Size, Insets and Rect; Dimension and Rectangle are errors naming Size and Rect. Sizes is still Jade's.

D180Rect takes all four numbers (part 7)

Rect(x, y, width, height) takes all four, with no defaults. Java's Rectangle() is Rect(0, 0, 0, 0) and Rectangle(w, h) is Rect(0, 0, w, h): both are compile errors as written, so that Rect(30, 40) cannot quietly mean the corner. Rectangle(other) is other, which is copied wherever it is kept. Point(), Size() and Insets() keep their zeros, as in Java. The reason first given, that WinterWolf has no constructors of other forms, no longer holds: secondary constructors came in part 8 (8.9a), and Color has them. Today Rect(30, 40) says only that width and height are missing.

Decided2026-11-03: Confirmed, with a change: still all four numbers, and Rect(30, 40)'s error says that x and y come first, as in Rect(0, 0, 30, 40) (done 2026-11-04, be8950e, 627e517).

D166Lists of values, as built (part 3)

  • A list is packed when it is given its type (by its literal, by what it is declared as, or at the call of a C++ function that made it): List<int>, List<float>, List<bool>, a value type's list, and the nullable ones of those.
  • Putting in a value the list was not made to hold is an error where it is put in (cannot put a value of type string in a List<int>), which an unchecked cast through List<any> used to allow.
  • A copy of a list (toList, slice, subList, reversed, + of two of one type) keeps its type and how it is kept.
  • sortBy and sortByDescending, for every list, call the selector once per item rather than twice per comparison (a million items sorted in 70 to 130 ms instead of 1.5 s). A selector with side effects sees fewer calls.
Decided2026-11-03: Confirmed as built.

D167Changing a value through its place (part 4)

  • A var field of a value is changed only through a place that holds the value: a var variable (local, global, or one a lambda holds), a var field of an object, an item of a list, a value's field that is itself a place, or a lambda's parameter (what forEach { it.move() } is given). So p.x = 4, p.x += 1, pts[i].y++, line.to.x = 9.
  • A mutating fun may change this's fields and call the type's other mutating methods, and is called only on a place. mutating on anything but a value type is an error.
  • A variable or field changed this way gets a value of its own first, so val q = p; p.x = 10 leaves q as it was.
  • Every part of pts[next()].x += 1 is worked out once.
  • Found on 2026-11-03: a lambda's parameter counts as a place wherever it is, but only some functions hand the lambda the item where it is. pts.forEach { it.translate(1, 0) } changes the list; pts.filter { it.translate(1, 0); true }, map.forEach { k, v -> v.translate(1, 0) } and g(pts[0]) compile, and the change is lost. for (p in pts) { p.translate(1, 0) } is an error saying the change would be lost.
Decided2026-11-03: Confirmed, with two changes: a for loop's item over a list is a place too, as forEach's is, so a changing call on it changes the list's item; and a lambda's parameter is a place only where the function hands it the item where it is (forEach, a parallel forEach), elsewhere a changing call on it is the "change would be lost" error (done 2026-11-04, e30f67f).

D168Reading a value where it is (part 4)

  • A value read from a list or another value (pts[i], a loop's item, a lambda's it, a parameter, this) is not copied where the checker shows that nothing which may change a list of its type runs while it is in use, through what the code calls, overrides included. Changing a list means removing, inserting, sorting, setting or replacing items; adding at the end is not, as a reference into a list is by position. A function given as an argument counts as one that may.
  • A loop is judged by its body. If the body gives the item to a variable from outside the loop, the loop is judged by the whole function, as the item might be used after it.
  • Since G10 (2026-10-24), pts[i] used at once (a field read from it, an argument, a comparison) is judged by its statement; kept in a variable, by its innermost for or while loop, or by the function where the statement may give it to a variable from outside the loop; in a lambda, by the lambda.
  • Since G35 (2026-11-02), code copied in from an inline function, and a lambda copied into it, read items where they are as code written there does.
  • A call that may wait counts as one that changes every list, since other code runs meanwhile: a flow that waits in a loop reads each item as it was when the loop came to it.
  • Whatever keeps a value longer than the stack does (a field, a list, a global, a variable a lambda holds, a C++ function) takes a copy.
  • The test setting WW_COPY_READS=1 copies every read; the suite prints the same with it.
Decided2026-11-03: Confirmed as built (the text above is brought up to date with G10 and G35).

D169Results built where they go (part 4)

  • pts[i] = f(...), where f gives a value of the list's type, gives f the item as where its result goes. A function that gives a value passes that on to a call whose result it returns, and making a value from its header alone writes its fields there, every argument worked out before any is written.
  • So pts[i] = pts[i].moved(1), pts[i] = Point(...) and pts[i] = pts[i].copy(x = 4) make no copy.
  • list.replaceAll { it.moved() } replaces each item by what the lambda gives, built where the item is.
Decided2026-11-03: Confirmed as built.

D170Parallel sections over a list of values (part 4)

  • pts.parallelStream() deals each core its own part of the list and hands it the items where they are: forEach { it.move() } changes them there, map and the rest read them there.
  • parallelStream().replaceAll { it.moved() } replaces each item, on every core, built where it is. On a list of anything else it puts what the lambda gave in once every core is done.
  • A core reads and writes only its own part (pts[0] from another core's part is an IllegalStateException saying so), and changes the list itself not at all (sortBy, sortByDescending and replaceAll now count as changing a list, as they should have already). A built-in function given the whole list is refused, but for isEmpty and isNotEmpty.
Decided2026-11-03: Confirmed as built.

ThreadsNo scan at a thread switch (part 4)

The plan was to replace a thread's references into lists by copies whenever it gives up the lock. Not built, and proposed not to be: a thread gives the lock up only at a call or the end of a loop body, and another thread reordering a list meanwhile is a race, which WinterWolf lets give a wrong answer but never damage anything. A reference into a list is checked against the list's length and its type of item every time it is used, so a race at worst reads or changes another item, as it would with objects. A flow is not a race (other code runs at the points where it waits, by design), and the checker handles it (D168).

Decided2026-11-03: Confirmed as built: no scan.

D171Small values in the value itself (part 5)

  • A value type whose layout is at most 8 bytes and holds no object (value Rgba(val argb : int), value Meters(val m : float), value Flags(var on : bool, var shown : bool)) is kept in the value itself: its fields in the 8 bytes a value has for its contents, its type's number beside them.
  • So in variables, arguments, results, fields, lists and maps it takes no box and allocates nothing. The program sees no difference.
  • C++ functions are given one in a box, as they are given every value of a value type; list.add excepted (D174).
  • Measured: bench/colors_values.ww, 100 frames of a 320 by 240 picture blended from a palette, 24 to 31% faster than in part 4, with no box made where part 4 made 15.4 million.
Decided2026-11-03: Confirmed as built.

D172Values inside their objects (part 5)

  • A field of a value type larger than 8 bytes, not null, is kept inside its object, after its other slots, laid out when the first object of the class is made.
  • comp.bounds = r copies the value's bytes in; comp.bounds.w = 30 and comp.bounds.origin.move(1) change it there; comp.bounds = Rect(...) and cached = measure() build it there.
  • A field is laid out so when its type is written, or when it is given a value made by its type's name (var cached = Size(0, 0)). A field of an object made before its class's field types exist keeps a box.
  • A reference into such a field has the same 16-bit offset as one into a list's item, so the 64 KB limit (Size, below) covers it too.
Decided2026-11-03: Confirmed as built. The check of the 64 KB limit (Size) covers these fields too.

D173Fields and results read where they are (part 5)

  • Giving a field of a value type another value counts, for D168, as a change to values of that type, as changing a list of them does.
  • A field kept inside its object is read where it is (a reference into the object) where nothing that may change values of its type runs while the read is in use; otherwise it is copied.
  • What a function gives back that it read where it is stays so where the caller is shown to be as safe; a call's result read at once by one of its fields (node.sizes().pref), and a field given back by return, always are. Elsewhere a function gives back a copy.
  • Measured: bench/layout_cached_values.ww, Jade's layout with each component's Sizes kept inside it, makes 1,215 boxes where part 4 made 57,126; its time is 4 to 7% more, from the reads through references (G14).
Decided2026-11-03: Confirmed as built. The 4 to 7% is G14's, in M6.7.

out.add(p) for an item read where it is, in a loop say, copies its bytes straight into out, with no box made for it on the way: filtering a million points by hand takes 43 ms instead of 65. add(i, item) copies the item first, since the items after i move.

D175Generic functions copied per layout: not now (part 5)

Measured on a million points in part 5: map 46 ms against 41 written out by hand, sumOf 25 against 23, filter 98 against 43, sortedBy 84. The check that generic code makes costs a few percent. filter's difference came from copying each item it hands to its lambda, since the lambda might change the list; inline functions remove that, and copies per layout would not. Inline functions (D59) came in part 8 (group 4), and since G35 (2026-11-02) code copied in reads items where they are: an inline function's body handing each item to its lambda now takes 43 ms against 52 for a plain loop. Copies per layout wait until a measurement asks for them.

D176A number's conversions and Math's functions as instructions (part 6)

x.toInt(), toLong(), toFloat(), toDouble(), roundToInt(), roundToLong(), isNaN(), isInfinite(), isFinite(), and Math.sqrt, floor, ceil, round, abs, and min and max of two ints or two floats, where the checker knows the call is the standard library's, are one instruction each, giving what the library's own gives, errors included. Drawing a million particles a frame is 34 to 40% faster.

D177Fields kept as their payload alone (part 6)

  • An int, a float or a bool field whose type is known (written, or worked out from what it is first given), and not null, is kept in its object as its 8 bytes of contents alone, before the object's slots, at the same place in every object of its class. An object of three float fields takes 72 bytes in place of 96: a million of them, 112 MB at most against 142.
  • A val, and a field an init must set, has a bit saying whether it has been given a value, so that giving a val a second value, and an init that leaves one unset, are still errors.
  • Any other payload reads as 0, 0.0 or false before it is first given a value, where a slot read as an error. (Only code that reads a field before the line that gives it its value sees the difference; Java's fields do the same.)
  • Field reads and writes are as fast as before, with Clang and with MSVC.
Decided2026-11-03: Confirmed as built.

D149Values in variables, in M6.7 (D178)

Values of up to 32 bytes kept in consecutive slots of a frame (D149) need the same change to how a frame's slots are laid out as frame slots that keep only a payload. You decided on 2026-10-19 (D178) that those, with instructions chosen by type for arithmetic, come with M6.7's rewritten loop. Until then a value larger than 8 bytes in a variable, an argument or a result is a box (gaps G8, G13 and G19).

Plan: M6.6.2, a sandbox for tests

Asked for 2026-11-04: a world for tests in which files, the network and processes are make-believe, so that nothing outside it is touched, and in which the test can make the rare failures happen on purpose (a directory that fails half way through being listed, a disk that fills, a connection that drops after 100 bytes). The user's answers to its four questions (2026-11-04) are under "Decided" at the end, and the text follows them. All seven steps are built (2026-11-04); where what was built differs from the plan below, "As built" at the end says how.

In short

Every file, stream, process and socket operation of WinterWolf is already a C++ function of the standard library's (__file, __io), and so are the clock, the timers, randomness and the installed fonts. The plan puts one C++ interface, the host, in front of all of them:

  • the real host is today's code, moved behind the interface and otherwise unchanged;
  • the virtual host keeps everything in memory: a file system, a network, programs to run, a clock that moves only when the program waits, a fixed random seed; and a list of faults that say which operation fails, where, when and how.

Every test of ww test runs on the virtual host, a sandbox of its own, unless it says @RealHost; any program may ask for one too, with Sandbox.run { ... }. Inside it, the real host cannot be reached at all: that is what makes "nothing outside is touched" a guarantee rather than a habit.

// Each test is in a sandbox of its own: Sandbox.current is it.
@Test fun reportsAHalfReadDirectory() {
  val box = Sandbox.current!!
  FilePath("/data").mkdir()
  for (name in ["a", "b", "c"]) { FilePath("/data/$name.txt").writeText(name) }
  box.faults.add(Fault.list("/data", after = 2, error = "the device is not ready"))
  val error = assertFails { FilePath("/data").list() }
  assertContains("${error.message}", "the device is not ready")
}

@Test fun survivesADroppedConnection() {
  Sandbox.current!!.network.host("example.test", 80) { peer ->
    peer.send("HTTP/1.1 200 OK\r\nContent-Length: 1000\r\n\r\n")
    peer.send("x".repeat(100))
    peer.reset()                        // the far side goes away 100 bytes in
  }
  assertFails { fetch("http://example.test/") }
}

@Test fun timesOutWithoutWaiting() {
  Sandbox.current!!.processes.add("slow") { process -> process.waitForever() }
  assertFails { Process.run("slow", timeout = 5.minutes) }   // takes no real time: the clock is the sandbox's
}

@Test @RealHost fun junctionsOnWindows() { ... }   // on the real system, for what only it can show

// In a program: a dry run of something that would change files.
Sandbox.run(copyFrom = FilePath("project")) {
  tidy(FilePath("/project"))
  print(files.changes())                // what it would have done, and nothing done
}

Java has Jimfs, Python pyfakefs and Go fs.FS and fake listeners for parts of this; putting the files, the network, processes, time and faults behind one interface, in the runtime itself, is what lets one test arrange all of them and reach the rare paths.

How each part works

Files. A tree of directories and files held in memory: contents as bytes, times, the write bit, symbolic links. Paths are of one style for a sandbox: Linux's (/data/a.txt) by default, on every machine, or Windows' (C:\data\a.txt, names compared without case) with Sandbox.run(paths = PathStyle.windows) or @Sandboxed(paths = PathStyle.windows) on a test, so that code that builds paths can be tested both ways on either machine. A size limit makes "the disk is full" possible. The temporary directory and the program's own directory are in it. copyFrom starts it with a copy of a real directory, read once as the sandbox is made.

Streams. A file stream reads and writes the virtual file; a pipe and a socket are a buffer between two ends, each end able to close, half-close or reset.

The network. Names resolve only to hosts the test declares; anything else is "cannot find host". network.host(name, port) { peer -> ... } gives a far side written in WinterWolf, run as a task of the sandbox, which reads what the program sends and answers; listen in the program makes a port a test can connect to with network.connect(port). No real socket is opened.

Programs. processes.add(name) { process -> ... } declares a program: it is given its arguments, environment and input, and writes output and errors, ends with a code, or never ends. Starting a program not declared is "cannot start".

The clock. Time in a sandbox moves only when everything the program is doing waits: a sleep, a timer, a timeout, a read with nothing to read. The clock then jumps to the next time something is due. A test of a five-minute timeout runs at once and the same way every time, and clock.advance(2.seconds) moves it by hand. Randomness starts from a fixed seed unless the test gives another.

Faults. faults.add(...) takes rules, each saying:

  • which operation: open, read, write, list, delete, move, permissions, connect, accept, send, start a program, and the rest;
  • where: a path or a pattern of paths, a host and port, a program's name;
  • when: always, the nth time, after so many bytes or names, after so much time;
  • what: an error of the kind the system gives (not found, no permission, the disk is full, the device is not ready, the connection was reset, the time ran out), a read or write that does only part, or a delay.

A fault goes through the same error path in the C++ as the real failure, so the program sees the same exception and message it would. That is the point: the rare paths are the real ones.

Nothing escapes. Inside Sandbox.run, every operation goes to the virtual host; there is no way to reach the real one, and an operation the virtual host has no form of throws "not available in a sandbox". Workers and the cores of a parallel section started inside it share it.

In tests and programs

  • Every test of ww test runs in a sandbox of its own, made empty for it (with @TempDir's directory in it) and gone when it ends; Sandbox.current is it. @Sandboxed(paths = PathStyle.windows) asks for Windows' paths.
  • @RealHost on a test, or on a whole file, runs it on the real system instead, for what only the real systems can show: Windows junctions, a real TCP stack, real programs. The suite keeps a small set of these.
  • Any program may use one: Sandbox.run { ... } runs the block on a new sandbox, and the block's own code, and the threads, tasks and workers it starts, reach nothing else. It ends with the block and leaves nothing behind. copyFrom starts it with a copy of a real directory, and files.changes() says afterwards what the block made, changed and deleted: a dry run.
  • What the sandbox did can be read afterwards for checks: files.read(...), what a peer received, which faults fired.

The test runner (tests/run.ps1) runs scripts as they are, on the real system: a script that wants a sandbox asks for one. The tests that touch files and the network today move into sandboxes as each part is built, and stop leaving or needing anything on the machine.

Cost

  • Speed: one indirect call more for each file, stream, process or socket operation, nothing beside a system call; nothing for code that does no I/O. The benchmarks are measured before and after step 1.
  • Work: about six to eight days in all, in the steps below. The most is in making the virtual files and network behave like the real ones closely enough to be trusted, and in the clock, which has to know when every thread and task of the program is waiting.

Plan: M6.7, a faster VM, and two changes to the language first

Started 2026-11-04, when the user said "start M6.7" after M6.6.2's checkpoint. What M6.7 is, is in gui-plan.html (M6.7) and M6.7-gaps.html; this file is the order it is built in, and what was decided along the way.

Order

The VM's rewrite is to come once the language has stopped moving, so the two changes to the language decided for M6.7 come first.

  1. Task scopes: taskScope { task { ... }; task { ... } } (Kotlin's structured concurrency). The decisions are below.
  2. use { } checked against each class's own close() (M6.6 choice 8.5i), so that AutoCloseable.close may say throws IOException.
  3. What the VM does now, measured: the benchmarks of M6.5 part 4, on the Clang and MSVC builds, best of five, the machine quiet (memory: the loop is sensitive to where it is placed).
  4. Instructions that name a frame's slots (registers, as Lua 5) in place of a stack, and combined instructions for common pairs (a compare and a jump, a field read and a call). Clang: each instruction goes on to the next itself through a computed goto, the code threaded as it is loaded (D160); MSVC: the cases of a switch. Bytecode files are made again.
  5. Slots that keep only a payload where the compiler knows the type, and arithmetic chosen by type, with no test of the operands' kinds (D178, G17; G20 and G58 if they show in timings).
  6. Values of up to 32 bytes in consecutive slots (D149): G8, G9, G13, G14, G19.
  7. A generic value type's type arguments kept when the program runs (G4).
  8. G66 if it shows in timings; then measured against step 3, the docs, and version 0.6.7.

Each step its commit or commits, with the quick check; the full check and Linux at the end of each.

Task scopes (step 1)

Decided by the user, 2026-11-04: a scope throws the first failure where it ends, where a try around it takes it; and what it may throw is worked out by the checker: what its block throws, and what the blocks of its task { } and thread { } throw, counted where the scope ends rather than where they are started, so that a try around a task { } inside the scope does not seem to catch it. A scope given to another function takes only lambdas that throw nothing checked.

As built:

  • task { } and thread { } in the block are the scope's (members of TaskScope, the block's receiver); add(job) makes any other job one of its own, a pool's submit { }; plain task { } outside a scope is as before.
  • The scope ends when its block and every job have ended. Where a job fails or the block throws, it cancels the other jobs, waits for them to end, and throws the first failure as it was thrown, later ones set aside in it (suppressed). A job stopping because it was cancelled is no failure. A scope that is cancelling starts nothing more. cancel() cancels it by hand: it then throws a CancellationException.
  • The block itself is not stopped: it goes on until it ends (its get() of a failed job throws).
  • Cancelling a task's job with interrupt = true (as the scope does) now stops the task where it next waits, with a CancellationException; a wait it was cancelled at leaves nothing behind (a delay's timer, a lock's hold on the event loop). A thread's job interrupts the thread, as before.
  • get() on the main thread outside a task runs the event loop until the job is done, and so does the scope's wait there: tasks waiting on timers go on, where before the wait could never end.
  • What the checker needed besides: a lambda run on an object called as obj.block() now passes on what it throws, as block(obj) did (it did not, for Sandbox.run too); and in a lambda run on a value of a built-in type (a string, an int) or a nullable one, a name the value cannot have as a member is looked for further out, as anywhere, where before the call was not checked at all.

use and close() (step 2)

AutoCloseable.close() says throws IOException. The standard library's use counts its own call of close() as throwing nothing; at each x.use { } the checker adds what the close() of x's type throws: a stream's and a pool's nothing, a class's own what it says, and through a type parameter or the interface itself the interface's IOException.

Going from one instruction to the next (step 4, first part)

Built with Clang or GCC, each instruction now ends by going straight to the next one's code, through a table of 256 addresses filled when the loop first runs (D160's computed goto); an instruction with no label of its own (none now) goes through the switch, and MSVC goes round the switch as before. With the jump at the loop's head alone, numeric was -16% but bounce_values and bounce_moved +3%: the compiler copied it into some instructions and not others. The register machine (step 4, the rest): design

Decided by the user, 2026-11-05: the full register machine, Lua 5's way, rather than moving the hot instructions to slots one family at a time.

Where register code comes from. The compiler goes on writing stack code, which the verifier follows already, knowing the stack's depth before every instruction. As a function is loaded, a translator turns that code into register code: every slot an instruction reads or writes named in the instruction, the stack's depth at each point telling which slot a pushed value is in. The compiler's 8,500 lines, the verifier and the bytecode files stay as they are; the stack code becomes what the compiler hands the translator. The VM runs only register code.

What the translator saves. A local or a constant that the stack code pushes only to be used at once is not moved: the instruction using it names the local's slot, or the constant (GetLocal a; GetLocal b; Add; SetLocal c; Pop is one instruction, Add c, a, b). A result that the stack code stores into a local is written there by the instruction that makes it. A comparison followed by a conditional jump is one instruction. Where a value pushed from a local might be read after the local has changed, the translator copies it first, as the stack did.

The frame. A frame's slots are its registers: its parameters, its locals, then the slots its stack code used as a stack, as many as the verifier's maxStack. A call's callee and arguments are in consecutive slots at the top, as now, and the called frame starts at the callee's slot, as now. sp_ is the top of the running frame's slots, set as a frame starts and as one returns (Lua's top): what the collector scans to, and where the C++ pushes when it calls back into the program. After marking, the collector clears the slots above each stack's top that hold anything, so that a slot coming back into reach never holds an object already collected.

Instructions rarely run. Of the 185 instructions, the ones the benchmarks run are given register forms of their own. The others are kept as they are, run on the stack: the translator puts what they take into the slots at the top, as the stack code had it, and gives each the depth it runs at, from which the VM sets sp_ before the instruction's old code runs. Their code needs no change.

What else changes. A catch block's handler keeps the slot the error is put in, from the depth at its TryBegin. A task set aside in a call keeps the slot its result goes to, as now. The threaded code of D160 and the typed slots of D178 come after, on the register code.

In parts, each working and measured. R1: the translator, one register instruction for each stack instruction, nothing saved yet, the VM run on it; no faster, but the machine is a register machine and every test passes. R2: locals and constants read where they are, results written where they go, comparisons joined with jumps; this is where the time is won. R3: the code threaded (D160). Then typed slots (step 5).

The register machine as built so far

Part A (56696d4): each function keeps the code the VM runs beside its stack code, made as the verifier passes it, with a line table and its rights' ranges in that code's offsets.

Part B: the translator (registers.cpp). It follows the stack code with the verifier's depths, noting a pushed local or constant instead of moving it; an R instruction names where its operands are, with the stack instruction it stands for after it, whole, which runs where its quick way does not do, its operands put where the stack would have had them. Every value noted is put in its slot before any other instruction, a jump or a place jumped to, and before an R instruction writes a slot above it, so that every slot below the VM's top holds what was written there while it was below the top, and the collector needs no change. A slot a nested function captures is never read through a note. Anything the translator does not expect keeps its stack code (WW_TRANSLATE_STRICT makes that an error, for testing it). All 360 tests pass on register code, with every stress setting.

It is not yet faster, and is made only with WW_REGISTER_CODE set. In the same build, numeric ran in 256 ms on it against 185 on its stack code, fields 160 against 110: the stack code's joined instructions (MulLocals, AddLocal, StoreLocal) had already taken as many instructions out as the R instructions do, and each R instruction costs more, decoding three 16-bit operands and testing for each whether it names a slot or a constant, a branch hard to predict.

Next: one-byte operands (a function needing more than 255 slots or constants keeps its stack code); an instruction for each kind of operand, slot or constant, so nothing is tested when it runs; a result written straight into the local it goes to, and a comparison joined with the jump after it. The stack code after an R instruction may be several instructions (Add; StoreLocal x, Lt; JumpIfFalse t), run in turn where the quick way does not do, so that an operator the program wrote, which pushes a frame of its own, still ends where it should.

Part C (2026-11-05): R instructions of a byte per operand, one for each kind of operand (slot and slot, slot and constant, constant and slot), so nothing is tested for it; a result written straight into the local the stack code stores it in; a comparison joined with the JumpIfFalse after it. Their slow way is out of line: the R instruction puts its operands where the stack would have had them and goes to the stack code it was made from, put after the function's own code, which comes back; so its quick way passes over a fixed length, nothing read to find where the next instruction is. RGetProp's quick way reads fields of values too (in a box, kept in the value, or through a reference to a list's item), as GetProp's does. A function needing more than 255 slots keeps its stack code. There is room for 35 such instructions: the stack code has 220.

Against the stack code in the same Clang build, best of five pinned: numeric -7%, calls -3%, bounce, particles and points the same, colors +2%, layouts +3% to +6%, simulation +5%, strings +7%, fields +35%. Small tests show why: where R instructions follow one another the register code wins (s += b.mass -24%, s += b.position.x -10%), and where an R instruction's result goes on to stack instructions it loses (b.position.x = 1.0 +12%: RGetProp, then Const and SetProp as the stack code has them). Still made only with WW_REGISTER_CODE set.

Next: R forms of the rest of what runs often (SetProp and SetOwn, GetGlobal, constants and Pop, the arguments of a call), so that stack instructions are rare in the code that runs most. That needs instruction numbers: the stack code's joined instructions (AddLocal, MulLocals, StoreLocal and the rest, some 30) never appear in run code, which has R instructions for them, so the run code can have numbers of its own, the translator turning even the stack code it keeps as it is (a function of more than 255 slots) into instructions without them.

Part D (2026-11-05), in six commits:

  • D1: the joined instructions are never in run code, and their numbers are the run code's own. The translator has three ways: in full (WW_REGISTER_CODE), joined only (the default, its joined instructions made R instructions: faster than the baseline everywhere, numeric -19%), and plain (a function of more than 255 slots; WW_REGISTER_CODE=plain to test it).
  • D2: R instructions for fields written (absorbing a statement's Pop), globals, upvalues, list items, - and !, JumpIfFalse. R instructions read their operands a field at a time where they are: a value just written in two stores is handed on by the processor to reads no wider than each, and a read wider than them waits for the stores to be done.
  • D3: where an R instruction's result goes where the stack would have it, its slow way is the stack instruction's own, at once, not out of line and back. A field read followed by another stays stack code, so GetProp reads a value inside an object through without copying it.
  • D4: shifts by a constant, & and |; quick ways that both kinds of code lacked: a string's or a list's size, a getter that only reads its stored field (as a property with a setter alone has), the fields of a value being made, in its box.
  • D5: fields read through a Ref of any depth (a method of a value held in a list's item); RGetProp writes its result in one store of 16 bytes (Value::setWhole), since what reads the whole value next (a call's arguments) waited for the two or three stores it made.

Two lessons from it. The slow ways that cost most were ones both kinds of code took; register code paid for each a jump out and back as well, so making them quick helped both. And the cost of an R instruction is mostly in how its result is stored and next read, not in the work it does. Writing every int and float result whole, as RGetProp's, was tried and cost more than it saved.

After D5, against the default in the same build: particles -14%, calls -10%, fields -9%, colors_classes -8%, bounce_values -6%, numeric -5%, the layouts -1% to -4%; points and strings within 1%; simulation +2% to +6% (building its grid: a map and lists, mostly native work). The same code built twice moves a benchmark by up to 5%, so differences under that are not told apart.

D6: the register code in full is the default (the user's choice, 2026-11-05, with simulation's gap left for later). WW_REGISTER_CODE=joined makes the code part D started from, and =plain the stack code, for testing and timing those ways; the suite passes in all three.

Threaded code (step 4, last part)

Each instruction of run code is now 8 bytes, then its opcode and its operands as before: built with Clang or GCC, the 8 bytes hold the address of the instruction's code in the loop, written the first time the loop runs the function (D160), so that each instruction goes on to the next with one load where it took two (its opcode, then the table). The translator is unchanged; a last pass (threadCode) puts the bytes in and moves every offset in the code, its line table and its rights. While an instruction runs, ip is past its opcode as before, so no operand is read differently; what reads the instruction after (readThrough) skips the 8 bytes. Code no path reaches is left out of run code now: copied as it was, its joined instructions read as the R instructions of the same numbers. Built with MSVC the bytes are not used.

Three measurements on the way. A table of addresses beside the code, one for each byte, was 12% to 14% slower (one more value to keep in a register). With the address in the code, clang merged the ends of most instructions into one shared jump, which the processor then predicts as one: numeric 10% slower than before; each end is now made different with an empty asm statement (WW_APART), which keeps them apart. Each instruction started at a multiple of 8 bytes, so that its address never spans two cache lines, was 1% to 4% slower than without.

Against the code before, in the same build: numeric -11%, points_classes -6%, fields -5%, colors_values -5%, bounce_values -3%; the rest within 2.5% either way. Run code is close to three times as large, as D160 expected (numeric's mandelbrot: 474 bytes, now 1,318).

Two-byte opcodes, and the instructions as functions (step 4, after threading)

Two-byte opcodes (b37f396): run code's opcodes are two bytes, so its own instructions have numbers of their own (275 in all) instead of borrowing the joined instructions'. Threaded, the opcode is not what takes an instruction to its code, and the byte costs only size. numeric showed +6.5%, which turned out to be where clang happened to place the loop's code: with its jump targets aligned to 16, 32 or 64 bytes numeric ran from 144 to 162 ms in either build, and profile-guided builds of both ran it the same.

Why the loop was a lottery. run() was one function of 32,000 machine instructions. Its state (frame, base, the VM itself) was kept in memory and loaded again in some 1,100 places; which of them kept a register changed with any edit (moving two stores spilled ip itself: +3% to +18%).

The instructions as functions (3a7056f, 8bb9f96, 5140de5, 9567d77, fe21996). run()'s cases moved to src/instructions.inc, written once with their ways out named (DONE, EXIT_RUN, JUMP_LABEL, CASES, FALL_INTO, GO_COLD). Built with Clang 19 or later, each is VM::tail<op>, a function that calls the next instruction's as its last step (preserve_none, musttail), with ip, sp, base, frame, consts, caches, code and the VM in registers from one to the next; the code holds each instruction's function, written as the code is made. Built with MSVC, GCC or an older Clang they are run()'s switch, as before. A proof on the hot instructions alone (branch m6-tail-proof) ran numeric 23% faster and the rest up to 18% slower, from going between the functions and run().

What it needed: run()'s base frame kept in the Context (the VM's threads take turns with one VM, and kept in the VM it was another thread's); three instructions' own values ended before they go on; no stack protector in the functions; and, built for Windows, where a function that calls anything sets up its stack frame as it starts whichever way it goes, each hot instruction's rare part a function of its own (COLD), so that the part that runs makes no call. Only seven registers are left to an instruction's own work, so a large one is split by kind (RGetProp: an object's field and an item's here, a value's in a box or held in another in its rare part).

Against the code before them (b37f396), same Clang build, best of five: particles -43%, calls -27%, numeric -20%, bounce_values -19%, colors -18% to -19%, bounce_moved -14%, fields and layout_classes -13%, points -10% to -12%, jade_layout -11%, the other layouts -7% to -11%, simulation -8%, bounce_classes -5%, strings -1%; against group 8, numeric -49%, particles -54%, calls -42%, fields -38%. All tests pass with Clang and MSVC in all three ways, with every stress setting and the sanitizer, and on Linux with Clang 21 (functions) and GCC (the switch).

Arithmetic chosen by type (step 5)

Typed arithmetic (8b52102, D178's second half, G17). Where the checker knows both sides of + - * / < <= > >= == !=, or of += -= *= /=, are ints, or both floats, it notes the expression, and the compiler emits an instruction of that type (ADD_I, MUL_F, LT_I and so on: 17 of them). The translator makes register instructions of them (R_ADD_I_SS, R_MUL_F_SK, R_JUMP_LT_I_SS and so on: 61), which read the two payloads and test nothing of what the slots hold. An int's sum, difference and product are still checked for overflow, and an overflow goes the general way, so its error is the same. An int divided by an int keeps its own rules and stays general, and so does a pair of mixed kinds such as 2.0 * i: the general instruction turns the int into a float there, which is what the program means. An int that may be null is typed once the checker knows it is not.

Against the tail-call build, same Clang build, best of five: numeric -21.8% (121 to 95 ms), fields -5.4%, bounce_values -4.8%, the rest -3% to +1%.

Not done: slots that keep only a payload (D178's first half). The general slot's kind byte is written along with the payload, and a typed instruction reads only the payload, so leaving the byte out would save one store per result; it waits until timings show that store.

Found on the way, and older than this step: a comparison worked out while compiling, of a NaN made from constants (0.0 / 0.0 >= 1.0), gave true for <= and >=, where worked out as the program runs it gives false. The checker compared through an order of -1, 0 or 1, on which a NaN fell as equal; it compares the numbers as they are now.

Values in variables (step 6)

Places (D149, G13, G19). A local variable whose type is a value type keeps its value in a place of its frame's, not in a box: val r = Rectangle(...), val s = child.sizes(), and the values made as arguments, Sizes(Size(1, 2), Size(3, 4), Size(5, 6)), make no object. D149 said consecutive slots of the frame; they are places beside the stack instead, which comes to the same for the program and leaves every instruction that reads slots as it was:

  • Each line of execution (a thread, a task) has 3,072 places, made when it first needs one and never moved. A function with such variables starts with EnterPlaces, which gives its frame a run of them above those of the frames under it; it has them until it returns. A frame for which none are left keeps boxes, as before (deep recursion).
  • Each place is laid out as a box is, with room for 64 bytes of value after it, and a variable holds a Ref to its place. To the interpreter a Ref to a place is a Ref to a box being made: no instruction tests which it is. (A first version kept the places as one block, a Ref saying where in it; the test that took in refClass, inlined into the instructions that read through a Ref, made reading an item of a list 75% slower, though no instruction run changed.)
  • A Ref is only ever on its stack. What keeps a value longer copies it, as for an item of a list (VM::own): a field, a list, a map, a captured variable when its frame ends, a value given back (copied into the caller's place where it gave one, WithPlace, or into a box), and a variable with no place of its own (KeepLocal: var keep : any = r).
  • A variable's frame alone changes its place, through it (p.x = 1, p.grow(), no box made: G8) or by giving it another value (SetPlace, a copy into it). A Ref read from it holds while its statement runs, unless the statement changes the variable inside it (f(p, p.also { p.grow() })): there the checker has the read take a copy (KeepTop). A lambda that changes a captured variable runs in a frame of its own, and gives the variable a box, so a call given the place meanwhile sees it as it was.
  • A call's result is made where it goes: in the variable's place, or, for an argument, in one of the statement's places; a function giving back a value kept in a place of its own copies it into the caller's.

Found on the way, older than this step: a value type with a property worked out by a getter (val size : Size get() => ..., as Rect, Size and Point have) was never made where it goes, the body's getters counted as fields that keep a value. They keep none now; with places, Jade's layout makes 42,000 boxes in 1,000 layouts where it made 397,000.

Against the build before it, same Clang build, best of five: layout_values -30%, layout_cached_values -17%, colors_values -6%, bounce_moved -3%, jade_layout level (with a tenth of the boxes); the rest within 3% either way.

A generic value type's type arguments (step 7)

G4, all of it as decided (the user's choice, 2026-11-05, over judging by the fields alone; in three parts: 28353cf, df54f9c, and the workers'). A value of a generic value type keeps the type arguments it was made with, or that the checker worked out, at no cost in bytes:

  • a box beside its class (the box's "being made" flag moved into the spare byte of the object's header, Obj::valueOpen), and a frame's place likewise;
  • a small value by a number of the VM's in its slot's refOffset, which a small value did not use; the number is kept on the type once given (ObjTypeInfo::valueNumber);
  • an item of a list, or a value kept inside an object or another value, takes them from the list's or the field's declared type, made for the object's own type arguments;
  • a phantom type parameter, which no field shows (value Id<T>(val raw : int)), where it is kept in a container declared wider than such a parameter can be (List<Id<any>>, a field Tag<any>, a value's field Id<any>), in a hidden 8-byte slot beside the item or field (option B); elsewhere nothing, the declared type saying it already.

  • What could be done, most useful first, to be tried when the loop is rewritten for D160:
    1. Profile-guided optimisation with Clang: a build that counts, the benchmarks run on it for a profile, and the build made from that profile, laying the hot paths out by how often they run rather than by where they are in the source. Interpreters usually gain 10 to 20% from it as well. Costs an extra build step with a training run, and a profile to make again as the VM changes.
    2. Alignment, such as -mllvm -align-all-nofallthru-blocks=5: every jump target starting on a 32-byte boundary, so that a change elsewhere does not move the hot cases. Cheap to try; it may help or slightly hurt, which only a measurement tells.
    3. A comparison that allows for placement: each side built in a few shuffled layouts (lld-link's function order) and the spreads compared, not one number. Nothing faster, but a real slowdown told from placement.
    4. Rare paths kept out of run(), as now (VM::typeInstruction, VM::placeInstruction, VM::classFinished). It helps, one change at a time.
