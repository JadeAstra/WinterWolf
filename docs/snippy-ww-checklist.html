Snippy and ww: a checklist

Made 2026-11-21 from a review of all of Snippy (lib/Snippy, 41 files, about 24,500 lines) against ww's standard library (src/std and the C++ behind it) and its libraries (lib/Crypto, lib/Web, lib/Formula), asked by the user: "make sure it uses something in ww rather than write its own, list anything that might fall under this", then "check on why they're different and if we should make ww give snippy's expected output". Snippy's measure is CPython 3.14's output, to the character; a piece of ww can take the place of Snippy's own only where it gives that output.

How to read it: checked is a finding seen again by hand (the code read, or the program run beside CPython); reported is a reviewer's finding not yet run. The owner says who does it: the files under lib/Snippy are the Snippy session's; src/std and the C++ are done wherever the user puts them. "After W1" and the like say what an item waits for. Paths below are from the repository's root; Snippy's runtime is lib/Snippy/Runtime.

1. Snippy's bugs: different from CPython today

  • S1int / int rounds twice done, 0.9.5072
    Runtime/Ops.ww:420 __pyBigTrueDiv
    Where an int is 253 or more and the quotient is not whole, it is p.toFloat() / q.toFloat(): each int rounded to a float, then the quotient rounded again, where CPython rounds once (long_true_divide). So the last digit can be off: 896756281784094569167941 / 826325471441701108669 is 1085.2337399445184 in Snippy, 1085.2337399445182 in CPython (two more cases found the same way). And an int past about 1.8×10308 becomes infinity before the division: (10**400 + 1) / 10**399 is an OverflowError ("integer division result too large for a float") in Snippy, 10.0 in CPython. Fix: since 0.9.5067, BigInt.divideToFloat (A1) is this division rounded once, as CPython's; __pyBigTrueDiv can be p.divideToFloat(q), with an OverflowError where it gives an infinity.
    Owner: Snippy session; easiest after A1.
    Done (0.9.5072, by the ww session at the user's word, "fix S1-S3, S5-S7"): __pyBigTrueDiv is p.divideToFloat(q) (A1), an OverflowError only where the rounded quotient is past the largest float: 896756281784094569167941 / 826325471441701108669 is 1085.2337399445182 and (10**400 + 1) / 10**399 is 10.0, as CPython gives them.
  • S2time.mktime reads tm_yday and leaves out the month and day done, 0.9.5072
    Runtime/ModTime.ww:482-489
    The date is pyYmdToOrd(year, 1, 1) + yday - 1; C's mktime uses year, month and day (normalising them) and ignores tm_yday, so mktime((2024, 3, 1, 0, 0, 0, 0, 0, -1)) gives 1 January.
    Owner: Snippy session.
    Done (0.9.5072, by the ww session at the user's word, "fix S1-S3, S5-S7"): mktime reads the nine numbers itself, as C's mktime: year, month and day, each carried past its range (month 13 the next January, month 0 the December before, day 0 the month before's last, hour 25 the next day), tm_wday and tm_yday not read; CPython's TypeErrors for a list or a tuple of other than nine.
  • S3str.isidentifier goes by category done, 0.9.5072
    Runtime/Methods.ww:767-778 pyIsIdentifier
    CPython goes by XID_Start and XID_Continue, which take in Other_ID_Start and Other_ID_Continue: '℘'.isidentifier() and 'a·'.isidentifier() are True there (CPython asked), False in Snippy. src/regex_unicode.inc already holds CPython's answers for identifier characters; reading them from there (or from W1's data) fixes it.
    Owner: Snippy session; with W1, or the regex table now.
    Done (0.9.5072, by the ww session at the user's word, "fix S1-S3, S5-S7"): pyIsIdentifier goes by XID_Start (or _) and XID_Continue, from a new table, lib/Snippy/Text/Classes.ww, made by tools/snippy/classes.py by asking CPython 3.14's own methods for every code point (as Unicode.ww and Case.ww are made); pyCharClasses in Text/Repr.ww reads it. collections.namedtuple and re's group names use it too.
  • S4str.isupper and islower go by category done, 0.9.5073
    Runtime/Methods.ww:621-640
    CPython goes by the Uppercase and Lowercase properties: 'ª'.islower() and 'Ⓐ'.isupper() are True there (CPython asked), False in Snippy. pyCharUpperCase and pyCharLowerCase in lib/Snippy/Text/Casing.ww:147-148 already answer these right.
    Owner: Snippy session.
    Done (0.9.5073, the user: "ww should gain what's needed and make them public, snippy shouldn't have anything of its own there"): Snippy has no case code of its own now. ww's upper, lower, isUpper and isLower were found to give CPython's answers for every code point; ww gained the rest, public: string.foldCase() (casefold, from CaseFolding.txt), title(), capitalize(), swapCase(), isTitle(), and char.title(), isTitleCase(), isCased(), isCaseIgnorable().   • S5NormalDist.samples without a seed makes a Random of its own done, 0.9.5072
    Runtime/ModStatistics.ww:300-307

  • S6statistics' own fsum done, 0.9.5072
    Runtime/ModStatistics.ww:111-124 pyFsum (and __pySumprodF 129-138, __pyFloats2 126)
    A second copy of math.fsum (ModMath.ww:640-657) that gives NaN before it looks for both infinities (CPython raises "-inf + inf in fsum" for [nan, inf, -inf], so fmean differs) and lacks ModMath's -0.0. Use ModMath's.
    Owner: Snippy session.
    Done (0.9.5072, by the ww session at the user's word, "fix S1-S3, S5-S7"): statistics' pyFsum, __pySumprodF and __pyFloats2 are gone; it uses math's, now pyFsum and pySumprodFloats in ModMath.ww. Checking against CPython showed the "-0.0" above was wrong: CPython 3.14's fsum gives 0.0 for [-0.0], and raises "intermediate overflow in fsum" where a partial sum passes the largest float though the exact sum does not ([1e308, 1e308, -1e308]), which math.fsum's exact sum missed. So pyFsum is now CPython's math_fsum step for step (Shewchuk's partials and the half-way correction); 3000 lists of every kind give CPython's results bit for bit.
  • S7str.isdigit and isnumeric from lists by hand done, 0.9.5072
    Runtime/Methods.ww:758-765
    The lists miss characters (the Ethiopic digits U+1369 to U+1371, most CJK numerals); CPython goes by Numeric_Type. A table made from Unicode's data (or from CPython, as Snippy's case tables are) would be whole.
    Owner: Snippy session; with W1's data.
    Done (0.9.5072, by the ww session at the user's word, "fix S1-S3, S5-S7"): isdecimal, isdigit and isnumeric go by Numeric_Type from the same table (S3); the lists by hand are gone. isalnum is CPython's too: a letter or any of the three.
  • S8A real minus a complex loses the sign of zero done, 0.9.5075
    lib/Snippy/Runtime/Ops.ww (mixed int, float and complex arithmetic)
    CPython 3.14 does mixed real and complex arithmetic as C11's Annex G does, without making the real a complex first: -1 - 0j is (-1-0j) there, its imaginary part -0.0, so cmath.phase(-1 - 0j) is -π. Snippy makes -1 into -1+0j first and gives (-1+0j) and π; 2 - 0j the same. Found while checking U20 (0.9.5074).
    Owner: Snippy session.
    Done (0.9.5075, the user: "fix these" (S8, S9, S10, U3, U17 and the list's missing range removal)): Snippy's mixed real and complex arithmetic is ww's own Complex and real operators, which keep the real a real as C11's Annex G does (-1 - 0j is (-1-0j), (inf+0j) * 0.0 is (nan+0j)). Checking found more: CPython 3.14's complex product and quotient recover infinities from NaN + NaN i (C11's _Cmultd and _Cdivd), and a real divided by a complex is Smith's way without an imaginary part for the real (2.0 / (-0+2j) is (-0-1j)); ww's Complex now does all three, checked against CPython over 13,581 products, quotients and rects of zeros, a subnormal, the largest floats, infinities and NaN (tests/complex_python.ww, numbers from tools/complex/python_complex.py). Powers: an infinite part is OverflowError: complex exponentiation, 0 to a negative whole power and an infinite phase (where C's cos and sin set EDOM) ZeroDivisionError: zero to a negative or complex power, as CPython's.
  • S9cmath.rect has no special values done, 0.9.5075
    lib/Snippy/Runtime/ModCmath.ww rect
    CPython's rect takes an infinite or NaN modulus or angle from its table of special values: rect(inf, 0.0) is (inf+0j) there, (inf+nanj) in Snippy (before 0.9.5074 too). With W6.
    Owner: with W6.
    Done (0.9.5075, the user: "fix these" (S8, S9, S10, U3, U17 and the list's missing range removal)): ww's Complex.fromPolar is CPython's rect, its table of special values too (derived from CPython over every kind of size and angle); Snippy's rect is fromPolar, with CPython's ValueError where the size is not 0 or NaN and the angle infinite.
  • S10No calendar module done, 0.9.5075
    lib/Snippy/Runtime/Modules.ww
    import calendar is ModuleNotFoundError in Snippy. isleap, monthrange, timegm, weekday and the like are now one line each over ww's LocalDate (U1).
    Owner: Snippy session.
    Done (0.9.5075, the user: "fix these" (S8, S9, S10, U3, U17 and the list's missing range removal)): import calendar works: a port of CPython 3.14's calendar.py (lib/Snippy/Runtime/ModCalendar.ww) on ww's LocalDate: the functions, Calendar, TextCalendar, HTMLCalendar and the Locale ones (C's names), each method called through the object so that a subclass's own is used; Day and Month as IntEnums (repr calendar.MONDAY, str 0, Day(3), Day['FRIDAY'], list(Month)), made by a small EnumType. For that Snippy's core now honours a metaclass's __getitem__ (before __class_getitem__), __len__, __contains__, __repr__ and a library metaclass's __call__, as CPython does. Not ported: calendar's command line (main). The EnumType is calendar's own until Snippy's enum module (5.3, step 5); then Day and Month move onto its IntEnum, so that there is one.
