Snippy and ww: a checklist

Made 2026-11-21 from a review of all of Snippy (lib/Snippy, 41 files, about 24,500 lines) against ww's standard library (src/std and the C++ behind it) and its libraries (lib/Crypto, lib/Web, lib/Formula), asked by the user: "make sure it uses something in ww rather than write its own, list anything that might fall under this", then "check on why they're different and if we should make ww give snippy's expected output". Snippy's measure is CPython 3.14's output, to the character; a piece of ww can take the place of Snippy's own only where it gives that output.

How to read it: checked is a finding seen again by hand (the code read, or the program run beside CPython); reported is a reviewer's finding not yet run. The owner says who does it: the files under lib/Snippy are the Snippy session's; src/std and the C++ are done wherever the user puts them. "After W1" and the like say what an item waits for. Paths below are from the repository's root; Snippy's runtime is lib/Snippy/Runtime.

1. Snippy's bugs: different from CPython today

  • S1int / int rounds twice checked
    Runtime/Ops.ww:420 __pyBigTrueDiv
    Where an int is 253 or more and the quotient is not whole, it is p.toFloat() / q.toFloat(): each int rounded to a float, then the quotient rounded again, where CPython rounds once (long_true_divide). So the last digit can be off: 896756281784094569167941 / 826325471441701108669 is 1085.2337399445184 in Snippy, 1085.2337399445182 in CPython (two more cases found the same way). And an int past about 1.8×10308 becomes infinity before the division: (10**400 + 1) / 10**399 is an OverflowError ("integer division result too large for a float") in Snippy, 10.0 in CPython. Fix: since 0.9.5067, BigInt.divideToFloat (A1) is this division rounded once, as CPython's; __pyBigTrueDiv can be p.divideToFloat(q), with an OverflowError where it gives an infinity.
    Owner: Snippy session; easiest after A1.
  • S2time.mktime reads tm_yday and leaves out the month and day checked
    Runtime/ModTime.ww:482-489
    The date is pyYmdToOrd(year, 1, 1) + yday - 1; C's mktime uses year, month and day (normalising them) and ignores tm_yday, so mktime((2024, 3, 1, 0, 0, 0, 0, 0, -1)) gives 1 January.
    Owner: Snippy session.
  • S3str.isidentifier goes by category checked
    Runtime/Methods.ww:767-778 pyIsIdentifier
    CPython goes by XID_Start and XID_Continue, which take in Other_ID_Start and Other_ID_Continue: '℘'.isidentifier() and 'a·'.isidentifier() are True there (CPython asked), False in Snippy. src/regex_unicode.inc already holds CPython's answers for identifier characters; reading them from there (or from W1's data) fixes it.
    Owner: Snippy session; with W1, or the regex table now.
  • S4str.isupper and islower go by category checked
    Runtime/Methods.ww:621-640
    CPython goes by the Uppercase and Lowercase properties: 'ª'.islower() and 'Ⓐ'.isupper() are True there (CPython asked), False in Snippy. pyCharUpperCase and pyCharLowerCase in lib/Snippy/Text/Casing.ww:147-148 already answer these right.
    Owner: Snippy session.
  • S5NormalDist.samples without a seed makes a Random of its own checked
    Runtime/ModStatistics.ww:300-307
    CPython's is rnd = random.random if seed is None else random.Random(seed).random: without a seed it draws from the module's generator, so random.seed(1) before it gives CPython's numbers; Snippy's does not.
    Owner: Snippy session.
  • S6statistics' own fsum reported
    Runtime/ModStatistics.ww:111-124 pyFsum (and __pySumprodF 129-138, __pyFloats2 126)
    A second copy of math.fsum (ModMath.ww:640-657) that gives NaN before it looks for both infinities (CPython raises "-inf + inf in fsum" for [nan, inf, -inf], so fmean differs) and lacks ModMath's -0.0. Use ModMath's.
    Owner: Snippy session.
  • S7str.isdigit and isnumeric from lists by hand reported
    Runtime/Methods.ww:758-765
    The lists miss characters (the Ethiopic digits U+1369 to U+1371, most CJK numerals); CPython goes by Numeric_Type. A table made from Unicode's data (or from CPython, as Snippy's case tables are) would be whole.
    Owner: Snippy session; with W1's data.

2. Snippy could use ww's code now, with the same results

Each of these is Snippy writing again what ww has, the results the same. Owner of all: the Snippy session.

3. ww to change: ww's flaws, whose fixes also give Snippy what it needs

  • W1Unicode data of ww's own for case and character classes checked
    src/builtins.cpp:96-124 changeCase; src/stdlib.cpp:110-205 charactersAre
    Outside ASCII, string.upper/lower and char.isLetter, isDigit, isWhitespace, isUpperCase, isLowerCase ask the operating system (LCMapStringEx and GetStringTypeW on Windows, the C library elsewhere), so one program can answer differently on Windows and Linux. The code says so itself: "the operating system's until the text engine brings Unicode data of our own (M4)". Case maps one character to one: "ß".upper() is "ß" (Kotlin's is "SS"). To do: tables made from Unicode's own files, the same everywhere, with full case mappings; one source shared with the regex engine's (src/regex_unicode.inc, and the \p classes the Snippy session is adding as 0.9.5067). Then Snippy's upper, lower, isalpha, isidentifier can use ww's (S3, S4); title case and casefold could be added beside them.
    Owner: as the user decides (D3); agree the table's home with the Snippy session first.
  • W2trim and split() know only ASCII whitespace reported
    src/builtins.cpp:168, 813
    Kotlin's go by isWhitespace, Unicode's. To do: W1's whitespace. Snippy's strip and split() could then use them, but for \x85, which Kotlin does not count and CPython does.
    Owner: with W1.
  • W3lines() leaves out a lone \r reported
    src/std/builtins.ww:118
    Kotlin's lines() breaks at \r\n, \n and \r. To do: as Kotlin. (Snippy's splitlines, which breaks at more and gives no empty last line, stays its own.)
  • W4char.digitToInt takes ASCII digits only reported
    src/stdlib.cpp:936-942
    Kotlin's takes any Unicode decimal digit. To do: as Kotlin, from W1's data. Snippy's int() of such digits (as CPython reads them) could then use it (Runtime/Builtins.ww:176-221).
  • W5Math.random, randomInt and seed differ from system to system checked
    src/builtins.cpp:700-728
    The generator (std::mt19937_64) is defined exactly by the C++ standard, but std::uniform_real_distribution and uniform_int_distribution are each C++ library's own, so a seeded program gets other numbers on Windows than on Linux. To do: ww's own step from the generator's numbers to a float (53 bits) and to an int in a range (without bias). Snippy keeps its own generator (CPython's Mersenne Twister, its seeding and state), so this is for ww's sake.
  • W6Complex as CPython's cmath at the edges reported
    src/std/complex.ww:120-226
    complex.ww says its functions "follow C99's and Python's cmath", but sqrt has no rescaling of subnormals and overflows past DBL_MAX; log lacks the branches past DBL_MAX/4 and under DBL_MIN, takes the 0.71 and 1.73 bounds the other way, and gives -inf for 0 where cmath raises; exp, sinh, cosh lack the exp(x - 1) e branch past 708.4; atanh's thresholds are 1e150 and 1e-150, not CPython's; tanh uses another formula (cut over at 20) and differs in the last digits even for ordinary values. To do: CPython's cmath algorithms in ww's Complex. Snippy's cmath (Runtime/ModCmath.ww, 270 lines) could then be ww's Complex.

4. ww to add: pieces both sides need

  • A1A BigInt divided by a BigInt, as a float rounded once done, 0.9.5067
    ww has BigInt / BigInt cut to a BigInt and BigInt / float as toFloat() / other, which rounds twice (src/std/bigint.ww:106). For S1, Fraction's __float__ (Runtime/ModFractions.ww:10-22), and any ww program dividing large ints.
    Done (0.9.5067, src/std/bigint.ww): BigInt.divideToFloat(divisor), the float nearest the exact quotient, as CPython's long_true_divide works it out: a quotient of 55 or 56 bits made by shifting one side, what is left over kept as a sticky bit, rounded once to the float's 53 bits (fewer for a subnormal quotient), halves to even; an infinity past the largest float, a zero with the quotient's sign. BigInt / float and float / BigInt now go the same way, rounded once (they were toFloat() and a float division: rounded twice, and NaN for two numbers past the largest float). +, - and * of a BigInt and a float still round the BigInt first. tests/bigint_divide.ww: 419 quotients of BigInts of 1 to 1200 bits (ties both ways, subnormal quotients, the edge of overflow) and 300 of a BigInt and a float either way, each the same bits as CPython's Fraction rounds the exact quotient to; made by tools/bigint/divide_cases.py.
  • A2A float's bits, frexp and ldexp
    Kotlin has toBits() and Double.fromBits; ww has none (Snippy goes through Bytes.putFloat64). For CPython's float hash (Runtime/Ops.ww:1101-1279), math.frexp (Runtime/ModMath.ww:11-24), float.hex and fromhex (Runtime/Methods.ww:1302-1361).
  • A3A floor and a ceiling that give a float name to decide
    Math.floor and ceil give an int by design (src/std/builtins.ww:725-729) and throw past 263, while Math.trunc gives a float; Kotlin's floor gives a Double. For Snippy's pyFloor and math.floor of large floats (Runtime/Ops.ww:204-208, ModMath.ww:791-800); lib/Formula needed one too (__fxFloor).
  • A4format's # flag (0x, 0o) and BigInt in %d and %x
    Java's formatter has both; ww's does not (src/stdlib.cpp:438-449). Part of Snippy's %-formatting could use it; its _ grouping and groups of four stay its own.
  • A5Writing JSON as it goes, to a Writer
    ww builds the whole text first (__JsonWriter). For json.dump and iterencode (Runtime/ModJson.ww:358-518), and for ww programs writing large documents.

5. Decisions for the user

  • D1format's rounding to decide
    ww rounds "%.1f" of 0.35 to 0.4, half up from the digits a float prints as, as Kotlin writes it (documented in src/std/builtins.ww:204-209); C, CPython and the exact value give 0.3. Keep Kotlin's, or round the exact value? Changing it changes what existing programs print. Recommended (quality over porting ease): the exact value.
  • D2The reach of Instant and Duration to decide
    Both are int nanoseconds, so an Instant reaches from 1677 to 2262 (src/std/time.ww:169) and a Duration about ±292 years. Java's, which ww's say they follow, are seconds and nanoseconds, reaching far past years 1 to 9999. Widening serves dates in history and lets Snippy's datetime (which reaches to 9999 with BigInt today) use them; epochNanoseconds would change. Recommended: widen.
  • D3What to start, and where to decide
    Sections 3 and 4 are ww's code (src/std and the C++); sections 1 and 2 are the Snippy session's. Recommended first: W1 (ww's answers differ between systems today, and S3, S4 and S7 wait for it), then W5, A1 and A2; the Snippy side after each.
  • D4A3's name to decide
    A float floor and ceiling: Math.floor giving a float for a float (as Kotlin's, changing what it gives today), or new names beside the int ones.

6. Kept as they are: ww's on purpose, or ww the more exact

  • Regex: after an empty match ww's findAll, split and replace go on as Java's do; split leaves out groups, replace writes $1, escape is \Q...\E, and split's limit is Kotlin's (src/std/regex.ww: "Java's syntax ... Kotlin's Regex around it"). Snippy has RegexOption.snippy and its own loops (Runtime/ModRe.ww:341-381, 517-558, 599-607).
  • Time: ISO text in one form (Instant.parse), __isoTime leaving out zero seconds, Java's pattern letters for formatting where CPython has %, Duration's text: all Java's. Snippy's ISO parsing, isoformat, strftime and strptime stay its own.
  • JSON reading: a lone surrogate becomes U+FFFD because a ww string cannot hold one (Snippy keeps its own, at private-use code points); a byte-order mark is refused; the hooks give ww's maps and lists; the messages are ww's ("string ... null"), its sort of keys ww's.
  • Map and Set go in the order things were put in, as ww chose (src/std/set.ww:3-5); CPython's set goes by its hash slots, and its hashes are its own (SipHash, the int hash modulo 261 - 1). Snippy's dict and set stay its own. Also: ww's map filters by a 32-bit hash before == and keeps the collector off while a key's == runs, neither of which a Python-like __eq__ could rely on.
  • Numbers: float.mod giving -0.0 (Kotlin's); Math.log(x, base) rounding once, more exact than CPython's two roundings (Snippy keeps ln / ln); Math.hypot of two (Snippy's, of any number and rounded once, stays); Complex.pow of a complex power as exp(w log z); ww's overflow checks on ints, which Snippy keeps rather than catching.
  • Different functions for different jobs: trimIndent (Kotlin's) and dedent; padStart and zfill; hexToBytes and bytes.fromhex; JSON's quoting and repr; string.format (printf's) and str.format.
  • EventLoop has no "run until this one is done"; asyncio keeps its own loop.

7. Snippy's own, with nothing in ww to use

For the record, the larger parts that are Snippy's because nothing in ww does them: CPython's hashing (Runtime/Ops.ww:1101-1279); gamma, lgamma, erf, erfc, fsum, fma, sumprod, comb, perm, nextafter, ulp and cbrt (Runtime/ModMath.ww); the Fraction type (ModFractions.ww); statistics' exact sums and the normal distribution's inverse (ModStatistics.ww); the Mersenne Twister and the variates (ModRandom.ww); strptime, ISO weeks, tzinfo and struct_time (ModTime.ww, ModDatetime.ww); re's templates and Pattern and Match (ModRe.ww); str.format, %-formatting and CPython's float formatting (Runtime/Text.ww); the Unicode category and printable tables and title case and casefold (lib/Snippy/Text); expandtabs, center, to_bytes, from_bytes; the lazy itertools; the C3 method order; the "Did you mean" suggestions; the Neumaier sum; timers kept in order (ww has no heap).
