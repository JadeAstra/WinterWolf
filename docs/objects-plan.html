Plan: programs of objects at speed

Written 2026-11-20, at the user's word ("write a plan for these"), after toww, the x86 emulator ported from Kotlin to WinterWolf, ran 45 times slower than the Kotlin: about 250,000 guest instructions a second against 10 million. Its agent suggested six changes to ww; each was measured here, and the plan is what the measurements say to do, in order. A plan with its questions for the user at the end; nothing is built until they are answered.

What a program of objects costs today

toww runs each guest instruction through VirtualMachine.runFast: the address mapped, the decoded instruction found and its bytes compared with memory (self-modifying code), the instruction's execute called through an interface, flags set through methods of EFlags, the timers and sound polled, interrupts looked at. Each is a few calls and many reads of fields through chains (vm.regs.flags.overflow). The JVM puts all of that in place and keeps the fields in registers; the VM does each step.

Measured 2026-11-20 on 0.9.5043, Windows, Clang build: a counted guest loop (ADD, INC, a store, DEC, JNZ) through toww's own fast loop ran 567,000 instructions a second with the VM alone, 580,000 with native code: native code gives this program nothing. ww --profile (built for this, 0.9.5043) on it:

WhereShare
runFast's own lines: mapping, the successor link, the mode, the counters, the hooks44%
the instruction itself (IncDecRegOp, ArithRegOp, MovMemOffsetRegOp, ...)~25%
flags (setBit, EFlags.current, updateZSP, the lazy ones)~17%
the bytes compared with memory (isCurrent, matches, physMatches)~14%
afterInstruction, executeOp themselves~6%

A sample waits for the next loop turn or call, so a short function's time is counted partly in its caller: runFast's share is the larger for it, the leaves' the smaller.

Part 1: field reads in native code never slower than the VM

A field of a slot's object is read by native code in 1 ns (the region looks at the place's cache, then reads the slot). A field of a global's object, and the second field of a chain, take 10 to 11 ns: twice the VM. The work:

  1. Find why, with WW_DUMP_NATIVE on the two loops of fields.ww: whether the region leaves for the VM at the read (a global read the region does not do, or an object it does not know the class of), or reads it the slow way each time round.
  2. Read a global's object as a slot's is: a global the loop never writes is read once as the region starts (as a field held for the region is, lookp), and its fields read through the cache.
  3. Read a chain's second field as the first: the object the first read gave, its class taken from the cache that read filled.

Gate: both rows of the table at 2 ns or less in native code, and no row of timings.html slower.

Built 2026-11-20 (0.9.5047): gate reached

The two loops' regions left at the field read for the VM each time round: the compiler writes the stack form (GET_PROP) where the object comes from a global or from another field, and the region did that form itself only for a value type's field or a field that held an object. It now reads any other field as the register form (R_GET_PROP) does: a number kept as its payload alone, as the place's cache saw it, into a register (getpi, getpf), and anything else into the slot (getpv), each checking the object's class as it runs. A global's field 9.6 ns to 1.8, a chain of two 11.4 to 1.8, with native code; the VM alone as it was. tests/native_stack_fields.ww: every kind of field read so, objects of two classes at one read, null on the way, fields changed meanwhile, the answers as the VM's. toww's counted loop as it was (its loop's time goes to calls, parts 2 to 4).

Part 2: methods that may be overridden, put in place behind a check

Today a small method of a class is put in place where it is called, behind a check that the object is of exactly that class (JumpIfNotClass; the call made as before where it is not). A method that overrides another, or one called through an interface, never is: the checker cannot say which class's method the call reaches. Yet at many calls one class does: toww's op.op.execute(this) reaches dozens of classes, but most interfaces and overrides in a program have one class that answers them at a given call.

  1. One class in the program. Where the checker finds a single class in the whole program (the libraries with it) that has the method, an interface with one class implementing it, or an override no class below overrides, the call is that class's method, put in place behind the same check. A class made later (a script, a program loaded) fails the check and is called as now: nothing can go wrong, only stay slow.
  2. The class each call has met. Where several classes have the method, the VM's own call notes the class it last met at the call (a cache by the call, beside the field caches); a region made from that call puts that class's method in place behind the check, as part 2.1 does. Native code alone: the VM's copy of the function cannot change once it runs.

Gate: icall.ww's override and interface rows at 2 ns or less in native code (one class), and toww measured with the methods so put in place.

Part 2.1 built (2026-11-20, 0.9.5055)

At the user's word ("yes, go ahead with part 2.1"). Where a call names a method of an interface, of an abstract class, or of a class with a supertype, the checker (noteSmallCall) looks at every class of the program an object can be of that has the method: one of the method's class or below it, not an interface or abstract. Where each runs one and the same body, of a class that is not abstract and not a value type, that body is the one put in place, behind the check that the object is of exactly its class, as a class's own small method is. Anything else (two bodies, an interface's own body, an extend's, an enum's, a method with several forms) stays a call. A class the checker cannot see (a script's, a program loaded later) only fails the check.

  • A class with a supertype. Its methods were never put in place: a bare name of a member it inherits is looked up on the object as the program runs. They now are. The body keeps its class's rights where it is put, as an inline function's does. A body that uses super stays a call.
  • A fault found on the way. The lookup of a bare name (implicitReceiver, for GET_IMPLICIT, INVOKE_IMPLICIT and the rest) judged access by the function's own classes alone, never by the rights of code copied into it: a protected member a body inherited was refused where that body was put in place, as it would have been for an inline function's. It now judges by the rights at the instruction (accessDeniedAt); a function that has such rights keeps no cache of names found not to be members.
  • Private methods. A private method is never looked for below its class: a member of that name there is another member (o-private-shadow), and a first try that took Tagged.name for Named's private name failed private_shadow.ww. Such a method of a class below, met on the way down, ends the search.
  • Bodies inside bodies. A body put in place behind the check is refused, before the check is written, where a body put in place would be: inside a copy of itself, or past four copied in each other. Before, only a call of the method inside itself was looked for there; with more bodies put in place, toww met the rest (a compile error, "a method put in place behind a check could not be").
  • What it costs the checker. The classes below a class come from the table the checker keeps for methods with several forms (countBelow), each method looked at once, each pair of files asked about once. toww's first run, nothing cached: checking 190 ms to 203, compiling 197 to 205 (more bodies put in place). A first try that looked at every class of the program for each method took 265.
  • Programs kept in the cache. The call names an interface, and the class whose body is copied may be in a file the calling file does not import. A kept unit is compiled again only when a file it depends on changes, so the body is taken only where its file is one the calling file depends on (CompilerSession::dependsOn: the files it imports, followed through, and those of its folder). In a program of one folder that is every file.

Part 3: a call that is made, cheaper

Where the method is not put in place (toww's execute, reaching many classes), a call costs 12 ns: finding the method by its name in the class's table, checking the arguments, making the frame, and going back. The work:

  1. Measure where the 12 ns go, with a C++ profiler on icall.ww (Windows Performance Recorder, or perf in WSL where the user installs it).
  2. A cache at each call of a method: the class last met and the method found for it, so that a call to the class met before goes straight to the method (no look-up by name). Several classes at one call keep the last few.
  3. Whatever else the measurement shows: a frame made with less (slots set to nothing that the function writes before it reads), the arguments' checks left out where the checker proved them.

Gate: a call of a method not put in place at 6 ns or less in the VM.

Measured first (2026-11-20, 0.9.5047): the crossing, not the look-up

One body, too large to be put in place, called each way 3 million times (calls.ww, calls2.ww in the measurements), ns each time round:

CalleeBody aloneFunctionMethodOverride, interface
an empty loop and a sum (its loop a region of its own), native code1.422.324.624.8

twelve sums (a whole function's region), native code4.621.522.7

  • Looking the method up by its name costs about 2 ns; an override or an interface nothing more than a method.
  • In the VM a call costs about 7 ns. With native code it costs 17: the callee's region entered (nativeEnter: the region found among the function's, its context set up) and left again at its RETURN, which the VM does; a callee whose loop is a region of its own enters and leaves that too. Native code makes a call dearer than the VM does, which is why toww, whose loop is calls to methods with regions, gains nothing from it.

So the work, in this order:

  1. A whole function's region returns itself: its RETURN done in the region (the result where the caller wants it, the frame gone), the VM handed the caller's next instruction, not the region's way out to the VM's own RETURN.
  2. A function's region entered cheaply: the start's word naming its region, not a search of the function's regions; the context's words that do not change from one call to the next (the VM, the tables, the units) set once for the frame's stack, not at every way in.
  3. The look-up skipped: each INVOKE keeps the class it last met and the method found for it.

Gate, in place of the one above: a call from native code to a method with a whole function's region at 8 ns or less over its body (calls2.ww's method row, 22.7 ns, at 13 or less); the VM's own call no slower; toww measured.

Part 3 set aside for part 4 (the user, 2026-11-20, as recommended). The crossing was looked at piece by piece: finding the region among the function's (cached in a trial, it saved nothing), setting up its context, the call into its machine code with its registers loaded and stored again, and the VM doing the RETURN and the caller's next instruction. About 10 ns are spread over all of them; what can go now is about 2 ns (the look-up kept at each INVOKE) and perhaps 1 to 3 (a region doing its own RETURN). The crossing itself goes with calls made by native code, part 5, on the emitter; these two small steps are left for after part 4.

The method cache built (2026-11-20, 0.9.5053)

After part 4, at the user's word ("as recommended": the method cache first, then part 2.1; part 2.2 and a region's own RETURN left until each can be measured). The register form of a method call (R_INVOKE) already had a cache, used for C++ methods alone. For a method of a class it now holds one word: a mark (bit 63), the class's number (bits 48 to 62) and the method (the low 48 bits). A class is given its number when it is finished (FinishClass), its methods set for good from then: from 1, never two classes of the process alike and never given again, so that a class gone and its number left in a cache can never be taken for another; past 32767, none, and that class's methods are looked up at each call as before. An object of the class in the cache: its method called, with no look-up. Any other: looked up by its name, as before, and the cache set to it. One word, written whole, so that no thread sees one class's number with another class's method. Whether the method's name is open to the call's code depends on the call alone, and is checked before the cache is set.

Part 4: objects made cheaply

Each object is made by its own new (the C++ heap's lock and search), linked into the collector's list, counted, and freed by its own delete when it is collected; its constructor is a call of its own. The work:

  1. Objects of the sizes most are made in (up to a few hundred bytes) taken from blocks of their size that the VM keeps, a block for each thread, and given back to it as they are collected: no lock, no search, no call to the system. Objects past that size as now.
  2. A constructor that only sets fields from its arguments (a data class, a class with a header and no init of its own) made in place: the object made and its fields written by the instruction itself, with no call.
  3. The collector's sweep walks the blocks rather than the list of every object.

Gate: an object of no fields at 10 ns or less, of two fields at 12 ns or less, and the suite's GC-stress setting as it is.

Step 2 built 2026-11-20 (0.9.5049): an object made with no frame for its initializer

Measured first: the first step was there already (each thread takes and gives back memory in blocks of its size, objectMemory::take and give, with no lock and no call to the system), so an object of no fields costs 21 ns, and one of two header fields 41: its initializer a call of its own. A class's initializer that only gives the header's fields their arguments, exactly as the compiler makes it (GET_LOCAL 0, GET_LOCAL k, SET_OWN, POP for each, then RETURN_INIT; no field of the body given a value first, none required), is seen so as the class is finished (VM::seeHeaderInit), and its objects are given their fields by VM::construct through the caches of those SET_OWNs, as their quick way writes them, with no frame: every argument checked first (the object's layout, a payload's kind, the field's declared type as checkFieldAssignment checks it), then all written; where one does not fit, the initializer is called as before. A dead object of a class is given back by the sweep with no call of a destructor through its table. The VM alone, best of three, each kind in a process of its own:

Fields of the body given constants, the same way (0.9.5050)

At the user's word (2026-11-20, as recommended once step 2 was in: the fields' values before the collector). A field of the body given a value where it is declared (var count = 0) is given it by a function the compiler makes for the class (its fields' function, called through a run of the VM of its own before the initializer), or inside a generated initializer after the header's arguments. Each is now seen as step 2's initializer is (planFieldsOf): a run of fields given an argument, each argument once, or a constant (a number, a bool, a char, null, an interned string), and done by construct through their SET_OWNs' caches, with no call; a class with an initializer of its own has its fields' function's work done so and its initializer still called. An expression of constants counts as its value, as the compiler works it out where the class is compiled (var square = 6 * 7 is given 42 so); a value made anew for each object (a list, an object) or read from elsewhere leaves the whole function to be called, as before, its constant fields with it. An object of two fields of the body given values, 46.6 ns to 30.0, the VM alone; the rest as they were. tests/header_objects.ww: every kind of constant, a header with fields given constants, a class with an initializer of its own, a list made for each object.

The collector step measured, and making an object made shorter (0.9.5052)

At the user's word (2026-11-20, "do the collector step"), measured before it was built. With collections held off (the heap let grow to 8 GB), short-lived objects were slower, not faster: an object of no fields 21 ns to 25, of two header fields 40 to 51, the memory of the objects collected, given out again while the processor still holds it, cheaper than fresh memory. Kept objects, 107 ns to 97: the collector's work about 10 ns of each. So sweeping blocks in place of the list of objects would win little of what an object costs; the step was not built, and at the user's word (2026-11-20, "Streamline making", with perf, which the user installed in WSL) the way to a made object was measured instead, on the Linux build with perf record -e cpu-clock (WSL gives no hardware counters).

What the profile showed, and what was done:

  • Part 4 was not taken in a program kept in the cache (on Linux every run after the first): a kept function makes its caches, and their count, as it first runs, and the class is finished before that, so planFieldsOf refused it. The caches are now asked for as an object is made (fieldsFromPlan): until the initializer has run once, it is called. Linux, two header fields, 40 to 34 ns.
  • A call of a class through R_CALL went its slow way, the stack's CALL and back, a fifth of an empty object's time: construct is now called from R_CALL's rare part itself, as a value type's maker was, a frame for an initializer returning where the call leaves its result.
  • Not with a bare enum entry among the arguments, not yet resolved (pendingEnums_): neither the new way nor the initializer's plan, which would have given a field of no type the name.

Windows, best of three, interleaved with 0.9.5051: no fields 21.0 ns to 18.2, two header fields 31.7 to 28.3, two of the body 29.0 to 25.8, a data class 30.9 to 28.7, kept 97.9 to 94.6. What is left of an empty object's 18 ns is spread thin: the loop's own instructions, the first stores into the new memory, the sweep and the giving back, the taking. The gate (10 to 12 ns) would take an object made by native code, memory taken a step at a time from a block, or a collector of generations: not in this plan.

Part 5: native code across calls, after the emitter

With parts 1 to 4, a loop of toww's kind does in the VM what it must, each step cheaply. Native code that keeps going across a call (the callee's own native code entered from the caller's, its frame made by native code) is the native-calls plan, whose spike failed its gate with Clang stencils; the emitter makes the calling convention ww's own. It is planned there, after the emitter's parts 1 and 2, and measured on toww.

What toww can do itself

Things the profile shows that are toww's to change, for its agent, whatever ww does (none needs anything of ww):

  • Self-modifying code found as memory is written, not as each instruction runs. Each instruction's bytes are compared with memory before it runs (14%). A write to a page holding decoded code can mark that page's instructions stale instead (toww already has writeChanged and checkSmcBefore for the bus's writes), and the run loop then compares only on a page so marked.
  • Devices polled when they are due. afterInstruction polls the timer, the keyboard and the sound after each instruction; each can say the instruction count it next needs looking at, and the loop compare one number.
  • The CPU's state in fewer objects. vm.regs.flags.overflow is three reads; the flags in fields of the CPU's own class, read as one int and its bits, are one.
  • Measuring with ww's profiler: ww --profile=out.txt headless.ww ..., the report's functions by total time and its lines.

Risks

  • Part 2's check. A method put in place for one class must never run on an object of another: the check is the one JumpIfNotClass already makes for the methods put in place today, and a test of every form (an interface, an override, a subclass made after, a class of a script) goes with it.
  • Part 4 and the collector. Objects in blocks change how the sweep finds them and how memory is given back; GC stress, thread stress and ASan at the part's end, and the memory a long run keeps (Program.memoryKept) compared before and after.
  • A part that gains little. Each is measured on its own; one whose gate is not reached is said so here and left out, as the native-calls spike was.
