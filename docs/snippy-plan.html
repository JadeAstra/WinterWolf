Written 2026-11-19 as part 5 of the scripting plan began ("start scripting plan part 5"). What Snippy is now

Read 2026-11-19 in C:\Users\sciss\IdeaProjects\Snips\src\main\kotlin\com\snips\snippy: a tree-walking interpreter in Kotlin, 3,448 lines (of which 636 are the editor's completion and help card), with 209 tests in 16 files (about 170 of them on the language; the rest on completion and help).

  • Has: Python's indentation, def with defaults and keyword arguments, lambda, class with inheritance and 30 of Python's special methods, if/while/for/try/except/else/finally, raise, import of other blocks, comprehensions of the four kinds, slices and slice assignment, ints of any size, floats and complex numbers, lists, tuples, dicts, sets and frozensets, 40 built-in functions, the collections.abc classes written in Snippy, Python's error names.
  • Snips' own: the Table module (the formula functions), values turned into cells and back (a bool shows as 1 or 0, a list of lists as a matrix, a dict with "v" as a styled cell), errors as #VALUE!, #DIV/0! and the like, imports that find a document's blocks, math sections and feature trackers, stepping (a run stopped at its n-th statement, its variables shown), limits (5 million steps, depth 200, collections of a million).

Where Snippy is not Python

Each is something a Python user would trip over. Two kinds: what Snippy lacks (a script using it fails to read or run), and what Snippy does differently (a script runs and gives another answer, which is worse).

LacksDoes differently
  • print, input, open, and so enumerate zip map filter any all hash id divmod hex oct bin format getattr setattr hasattr callable super object
  • Generators and yield; with; decorators; global, nonlocal, del, assert
  • *args, **kwargs, keyword-only and positional-only parameters, * and ** in calls and displays, starred assignment, chained assignment, the walrus
  • f-strings, triple-quoted strings, r/b prefixes, \x and \u escapes, % formatting, str.format
  • Hex, octal and binary literals; ~, @, <<=, >>=; ; between statements; backslash continuation
  • for/while ... else; except (A, B); bare raise; raise ... from
  • Most methods of str (split with maxsplit, strip with characters, format, isdigit, zfill ...), list.sort(key=..., reverse=...), attributes of numbers (z.real)
  • bytes, bytearray, properties, classmethod, staticmethod, super(), __hash__, __enter__/__exit__, reflected operators (__radd__)
  • The standard library: math random re json collections itertools functools string time datetime and the rest
  • Defaults evaluated at each call (Python: once, as the function is made)
  • a < b < c is (a < b) < c (Python chains it)
  • xs += [1] makes a new list (Python extends the one there, which its aliases see)
  • try ... else: the else's errors are caught by the same except
  • No global: x = x + 1 in a function reads the outer x (Python: UnboundLocalError)
  • A float printed to 15 digits: 0.1 + 0.2 shows 0.3 (Python: 0.30000000000000004); 1e-05 shows 1e-5
  • type(x) gives the name as text; range gives a list; dict.keys() a list
  • repr of text always in single quotes, nothing but \ and ' escaped
  • Tuples cannot be ordered; a list never equals a tuple (right) but not, and, or ignore __bool__
  • An exception made without __init__ drops its arguments, so ValueError("msg") has no message
  • Some errors no try can catch (min([]), a method given too few arguments)

The design

The pieces, in WinterWolf

  • Reading: a lexer and parser for Python 3's grammar (as of Python 3.14, the version CPython has in this machine's WSL), giving a tree with each node's line and column; Python's own SyntaxError messages where it can.
  • Translating: Python's scopes worked out as CPython does (which names are local, global, free, and the cells closures share), then the tree made into WinterWolf source: one function for each Snippy function, each value any?, each operation a call of the runtime (a + b into Py.add(a, b)), so that Python's rules live in one place. Each line of the made source carries the script's line it came from, so that errors and tracebacks name the script's own lines.
  • The runtime: Python's values and their rules, its built-in functions, and the modules of its standard library that ordinary scripts use, in WinterWolf (as lib/Snippy, carried inside ww.exe as Jade is).

Python's values as WinterWolf's

Where WinterWolf has a value of the same nature, a Snippy value is that value, so that what a Snippy script gives or takes crosses to WinterWolf code and to a script's api (part 2's contracts) as it is: None is null; a bool a bool; an int an int, made a BigInt where it outgrows 64 bits (Python's ints have no end) and back where it fits; a float a float; a complex a Complex; a str a string; a list a list; a dict a map and a set a set (both keep the order things were added in, as Python's dict does). A tuple, a frozenset, bytes, a range, a function and a class are the runtime's own classes; an object of a Snippy class has its attributes in a table of its own, as Python's do, so that they can be added as it runs. Each operation asks what it was given and does as Python does: 1 + 2.5, "a" * 3, [1] + [2], an object's __add__, then the other's __radd__.

The harder parts, and how

  • Generators on WinterWolf's tasks, as sequence { yield(...) } already is: a generator function made into one whose body runs as a task that hands each value over; send, throw, close and yield from on the same.
  • Exceptions: a Snippy exception thrown as one WinterWolf throwable carrying the Snippy object, so that try, except by class (with Python's class hierarchy), finally, with and tracebacks all work; errors the VM itself throws (a division by zero, an index out of range) turned into Python's (ZeroDivisionError, IndexError) where they are caught.
  • Classes: Python's method resolution order (C3), super(), properties and descriptors, classmethod and staticmethod, class attributes, the special methods Python looks up on the class.
  • Text: Python's repr and str for every value (a float as the shortest text that reads back as it, as Python's), format and its mini-language, f-strings, %; a str indexed by code point, as Python's is (WinterWolf's strings count UTF-16 units).

Snippy programs and scripts

  • ww app.snippy runs one and ww build --exe app.snippy builds one, through the same pieces: the ending picks the reader; the made source is compiled as any program, cached as any, in the five ways. A Snippy program is trusted, as a .ww one is: it prints, reads its arguments (sys.argv), opens files.
  • A Snippy script is a Script like any (Script.compile(source, language = Language.snippy, ...)): safe unless trusted, limited, given an api and giving hooks as part 2 made them.
  • What Snips alone needs (its Table module, its cells, its blocks found by import, stepping) is Snips' part, for when Snips runs on WinterWolf (the formula plan); this part gives it what it needs to hang those on: an import resolver the host gives, modules the host makes, a hook at each statement.

Speed

Each operation a call of the runtime, as decided: about what Snips' interpreter pays, faster for what the VM's native code takes over (a loop's counting, a call's frame). Made into typed code where it knows the types, later, where scripts need it.

Questions for the user

1Where Snippy and Python differ: which way?

  • Python's way: what a Python user expects; Snips' documents that lean on Snippy's ways (a default made each call, 0.1 + 0.2 showing 0.3 in a script's repr, type(x) as text) give Python's answers once Snips runs Snippy here.
  • Snippy's way: Snips' documents unchanged; a Python user trips over each.

Recommended: Python's way throughout, as the user's reason for Snippy asks; the differences listed above written into the guide for Snips' users. (A cell still shows 15 digits: that is Snips' display, not the language.)

Decided2026-11-19, the user: Python's way (as recommended).

2How much of Python's language?

  • All of it but async/await: generators, with, decorators, every parameter kind, f-strings, match, the walrus, starred forms, global/nonlocal, type annotations (read and kept, not checked, as Python does).
  • All of it: async/await too, on WinterWolf's tasks; little used in the scripts this is for, and asyncio is a large module.
  • What ordinary scripts use: leave match and the rarer forms for later.

Recommended: all but async/await, which can come later on the same tasks.

Decided2026-11-19, the user: all of it, async/await too, on WinterWolf's tasks (not as recommended). So 5.1 reads every file of CPython's library, the 27 with async among them, and asyncio's core goes with 5.2's generators.

3Which modules of Python's standard library?

  • For every script: math cmath random string re json collections itertools functools operator copy time datetime statistics fractions textwrap dataclasses enum abc typing (the last as names only, as Python itself checks nothing).
  • For trusted programs too: sys os os.path pathlib io and open, refused in a safe script as files are.
  • Later, or never: decimal (large), asyncio, subprocess, socket, threading, tkinter, sqlite3, urllib, and C extensions such as numpy (which could not be).

Recommended: the first two lists; the third as asked for. re on WinterWolf's regular expressions, with Python's syntax where they differ.

Decided2026-11-19, the user: the common modules for every script, and sys os os.path pathlib io open for trusted programs (as recommended); the rest as asked for.

4Which file endings?

  • .snippy alone, as the user wrote.
  • .snippy and .py: a script in a .py file run as it is (ww hello.py), which is what "feed it python scripts" means at the command line.

Recommended: both.

Decided2026-11-19, the user: both, .snippy and .py (as recommended).

  • Both ways now.
