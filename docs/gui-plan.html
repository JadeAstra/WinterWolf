1. Goal and ground rules

Give WinterWolf a GUI library with the same API as JadeUI (jadelib-ui): every public function and parameter keeps its name, order and default, and every class keeps its name without the Jade prefix (JadeCanvas is Canvas), so that an app written against JadeUI in Kotlin is ported by translating syntax, not by redesigning its UI code. The deliberate differences are listed in section 6.

In WinterWolf the library is called Jade (import Jade, or import Jade.* for bare names). "JadeUI" in this document always means the Kotlin original. Sections that describe the Kotlin library use its names (JadeComponent); sections about WinterWolf use Jade's (Component).

The names before: until 2026-11-07 the language was Astra (its files .astra, its program astra.exe) and the library Jade; from then until 2026-11-13 the language was Jade (its files .jade and .jc, its program jade.exe), the library Topaz and the game engine Carnelian. On 2026-11-13, at the user's word, the language became WinterWolf (Jade being also Jade Software's programming language and the old name of the template language Pug), the library Jade again and the game engine WinterWerewolf. This document, the code and the commits since then use the new names throughout, and only the commits before say the old ones.

  • The library is written in WinterWolf.
  • C++ is used only for what a script cannot do: windows, input, drawing, text, images, clipboard, file dialogs.
  • Whatever is done in C++ is open to every program (the user, 2026-10-17): each piece has a WinterWolf API of its own, as public as any library's, so programs and other libraries get the same speed the library that needed it gets. The text engine, PNG, the software drawing engine, cryptography, and M13's physics, spatial grid and vector maths are each usable on their own, never only from inside the one library that asked for them. Raw built-ins (__text, __jade) stay internal; the public face is ordinary WinterWolf types. As long as opening it does not cost the library that uses it its speed: the public API adds no copy, check or extra call on the path WinterWolf's own libraries take (they may use the same API, or a faster internal one where the public one must check more), and a piece whose fast path depends on staying inside (the text engine's glyph caches, the renderer's batches) shows what it can without giving that up.
  • No Kotlin and no JVM anywhere in WinterWolf. JadeUI is the specification, not a dependency.
  • WinterWolf being a good language comes before porting Kotlin easily (the user, 2026-10-17). Porting is done once, but WinterWolf's speed, stability and readability matter for every program ever written in it, so they come first. The porting question is whether WinterWolf can do what the code does as well or better, not whether the code compiles unchanged.
  • WinterWolf stays self-contained (the user, 2026-10-17): ww something.ww runs with nothing else installed, and a built program needs no ww.exe, sources or lib. No milestone may require more; M14's native code stays an option beside built programs that need no C++ compiler.

The full list of names to match is in jadeui-api-inventory.md (machine-extracted; check a signature against the Kotlin source before relying on it). It lists the Kotlin names; apply sections 6.1 and 6.2 to get Jade's.

How it works, in the terms that matter for a port:

  • It draws everything itself. A widget is a JadeContent (reports sizes(), paints onto a JadeCanvas, handles JadeEvents) wrapped in a JadeComponent (id, bounds, visibility, colours, size overrides, paint cache). There are no native controls, menus or popups: menu bars, dropdowns, context menus, tooltips and dialogs are all Jade-drawn.
  • JadeCanvas is small: colour, font, fill/draw rect, round rect, oval, line, polyline, polygon, drawString, drawImage, measure, sub (a translated, clipped child canvas). Everything richer (SVG, charts, picture editing, HTML effects) is done by drawing into an offscreen image with Java2D and blitting that.
  • It is headless-first. A tree can be laid out, painted to a RecordingCanvas (a list of DrawOps) and driven with synthetic events with no window. Most tests work this way.
  • The host is not thin. About 1,200 lines of the GLFW backend are policy: press capture, focus rules, Tab traversal, popup-versus-press rules, context menu on right release, dropdown opening, tooltip timing, caret blink, hold-to-repeat, click counting, when to flush paint caches. The JavaFX backend duplicates it.
  • One UI thread. The only real background thread in the core indexes lines for the large-text view.

Decisions built into this shape:

  1. The host policy moves into WinterWolf. The native layer delivers raw events (pointer, wheel, key down/up with physical key and layout letter, text, focus, resize, scale change, close request, file drop) and nothing else. A window is a Window, the one class that replaces JadeUI's JadeHost, JadeWindow and WindowSpec (section 6.1). The Kotlin backends' own host classes are not part of Jade under any name: nothing in WinterWolf is called after GLFW or JavaFX.
  2. The native canvas mirrors Canvas (JadeUI's JadeCanvas) and adds persistent offscreen surfaces, because the per-component paint cache and the retained window buffer both depend on them.
  3. One UI thread, in a runtime that has threads. Layout, painting and input all run on the thread that runs the event loop, as in JadeUI. Caret blink, tooltip delay, hold-repeat and scheduled tasks are polled against a clock in the Kotlin frame function; here they are timers on that loop. WinterWolf itself gains threads and async I/O (section 5.5), so an app does its slow work off the UI thread, as the Kotlin apps do, and hands the result back through Jade.scheduler. The native layer must repaint from inside the resize callback (Windows runs a modal loop while a window is being resized), and runs file dialogs and image decoding on worker threads, delivering their results on the loop.

  4. The old gui library is no longer supported and is removed. Jade is WinterWolf's only GUI library. The old one receives no fixes from now on, and its files leave the tree in M5, when Jade's native layer replaces its backend:

    • lib/gui.ww and src/gui.cpp, with the references to them in CMakeLists.txt, src/builtins.cpp, src/compiler.cpp, src/main.cpp and src/vm.h;
    • the five examples/gui_*.ww and tests/gui_widgets.ww;
    • the GUI section of the README.

    Only its own examples and test were ever written against it, so nothing is kept for compatibility and nothing is migrated; Jade's examples are written fresh. Its Window and Color names pass to Jade. Three behaviours of the old backend are worth repeating in the new native layer: a window shows the icon of a program built with --icon; an error raised inside an event handler is reported instead of being lost in the message loop; and sizes follow the display's DPI.

Speed

Measured on the current VM: 15 to 25 million method calls a second, and laying out and painting 2,000 simple widgets takes about 0.4 ms. Ordinary widget trees are not a concern. Three things are: per-pixel loops (treemap shading, flood fill, blur), text layout of very long documents, and regex-heavy parsing (CSS, Markdown). Those get native helpers rather than script loops; the plan marks where.

4. The native layer (C++)

Drawing is done with OpenGL. Every window is an OpenGL window, and rectangles, text, images and the widgets' cached pictures are all drawn by the graphics card. This is the choice JadeUI's own GLFW backend points to, and it is made for the 3D view: JadeGen puts an OpenGL view inside the window and JadeUI draws menus, popups and tooltips over it. In a window that is OpenGL throughout, that is three layers drawn in order (the interface, the 3D view, the popups). In a window drawn any other way the 3D view either hides whatever should cover it or has to be copied in every frame.

How the pieces map onto OpenGL (3.3 core, the version JadeUI's backend and JadeGen use):

  • Shapes. A small renderer of Jade's own: batched quads, with the edges of rectangles, rounded rectangles, ovals and lines smoothed in the shader. Colour with alpha is ordinary blending.
  • Text. OpenGL has none, and Jade's comes from an engine of its own, with no third-party code: it reads font files, measures, and rasterises glyphs once into a texture from which they are drawn as quads. Described under the tiers below. Measuring works with no OpenGL context, because the recorded-drawing tests measure text without ever opening a window.
  • Offscreen pictures. A widget's paint cache is a texture drawn into through a framebuffer and blitted from then on. The window keeps its last picture the same way, so a small change redraws a small rectangle.
  • Clipping and offsets. The scissor rectangle and a translation. HiDPI is a scale.
  • Several windows. One context per window, all in one share group, so cached textures and the glyph atlas are shared, as in the Kotlin backend.
  • No window on screen. A hidden context drawing into a framebuffer, read back with glReadPixels.

What OpenGL does not give and has to be supplied: text (above), reading and writing image files, and the window itself with its input.

The window and its input are written by us, directly against Windows, with no third-party code: a Win32 window with a WGL context, a window procedure that turns Windows' messages into the raw events listed in section 3, the clipboard, cursors, file drops, and the built program's icon. It is about two thousand lines, and the old gui backend already had its beginnings (a window class, the message loop, DPI handling, timers).

It sits behind a small interface: create a window, deliver events, set a cursor, read and write the clipboard, wake the loop. That interface is the only part of Jade that is written per system. OpenGL drawing and the text engine are the same everywhere, so running on another system later means writing this one layer again for it and changing nothing in the toolkit. Two cautions for when that day comes: macOS's windowing is written in Objective-C, and Apple has deprecated OpenGL there, where it still works but is frozen at an old version.

The text engine

Text is Jade's own, in C++, with no third-party code and nothing asked of the system except which font files are installed. The requirement is that text works the same everywhere: measuring and positioning are reliable. It does not have to match any system's own rendering. It is a complete engine from the start, not a subset to be extended later.

Reading fonts

  1. TrueType and OpenType files and collections (.ttf, .otf, .ttc): which glyph a character maps to, each glyph's width, the font's ascent, descent and line gap.
  2. Both outline formats. Quadratic outlines, as in the fonts Windows ships, and the cubic outlines of .otf fonts, which are a small program per glyph that has to be interpreted. The second kind is common on Linux and in Chinese, Japanese and Korean fonts.
  3. Variable fonts. One file holding every weight and width, with each glyph's outline and width adjusted for the instance asked for. Windows 11's default interface font and macOS's system font are both of this kind, so Jade uses them as they are.
  4. Finding fonts. The system is asked only for the installed font files. Jade reads their names to match a family, size and style, and their character tables to find another font when the chosen one lacks a character.

Laying text out

  1. Shaping. Turning a run of characters into the right glyphs in the right places, for every script and not only those where one character is one glyph: the joined forms of Arabic, the reordering and conjuncts of the Indic scripts, combining marks placed on their bases, and emoji sequences that join into one picture. This means an interpreter for the substitution and positioning tables fonts carry, plus the rules particular to each script.
  2. Direction. Right-to-left text, and lines that mix both directions, put into visual order by the Unicode bidirectional rules.
  3. Unicode character data. Script, joining behaviour, combining class, direction and cluster boundaries for every character, built into the runtime as tables. This is data published by Unicode, not code, and it is the one outside input the engine has.

Measuring and positioning, by one rule

  1. A glyph's width is its width in the font scaled to the size and rounded to a whole pixel, and a run's width is the sum of its glyphs' widths after shaping. Each glyph is placed by adding up those widths, so measuring and drawing use the same numbers and a caret cannot drift from its text. On a scaled display the rounding has to happen in device pixels, or spacing comes out loose (found in M0). The clause, as settled in M4: a font is made for a size and a scale, and every number it gives is in device pixels, each glyph's width rounded there. A size in logical pixels is the device number divided by the scale, taken of a whole run and never of one glyph at a time; where the toolkit wants a whole number of logical pixels for a run (FontMetrics.stringWidth), it rounds that quotient up, so the text always fits the room measured for it. At a scale of 1 the two are the same.
  2. Shaping applies what a script requires and leaves optional typography off: no kerning and no discretionary ligatures. For Latin, Cyrillic, Greek, Chinese, Japanese and Korean a string's width is therefore still the sum of its characters' widths, which is what JadeUI's caret arithmetic assumes, and that arithmetic is exact. For scripts that are shaped, measuring part of a string shapes that part on its own, which is how the Kotlin version behaves through Java's text today: carets are approximately right, as they are now. Making editing exact in those scripts would mean carets that move by cluster and selections in visual order, which is a change to the ported text widgets and not to the engine; it is not part of this plan.

Drawing

  1. Rasterising. Each glyph's outline is turned into a small antialiased picture, once per font, size and instance, and kept in the atlas.
  2. Hinting. A simple rule of Jade's own that snaps the baseline and the tops of letters to whole pixels, so small text has crisp horizontal edges. The programs fonts carry for this are not run.
  3. Colour emoji. The layered-colour format Windows' emoji font uses, in both its versions (flat layers, and the newer one with gradients), drawn into a colour atlas beside the one for ordinary glyphs. The bitmap-based formats other systems' emoji fonts use are read too, which needs a PNG decoder of Jade's own.

What to expect of it

  • Reliable metrics and positions on every system, and identical pictures wherever the same font file is used, so even pixel tests of text are portable.
  • Small text a little softer than Windows' own on a screen at 100% scaling, since Windows runs the fonts' hinting programs and Jade does not. On a HiDPI screen the difference all but disappears. JadeUI on the JVM is drawn with Java's antialiased text today, not Windows', so this is close to how the apps look now.
  • Each system's own default font, so numbers differ between Windows and macOS where the fonts differ. Shipping one font with Jade would make them equal as well; nothing in the design depends on that choice.

How big this is. Points 1, 2, 4, 8, 10 and 11 are a few thousand lines and are what the first window needs. Variable fonts and colour emoji are each a bounded addition. Shaping, direction and the Unicode data (points 5 to 7) are the bulk: the library the rest of the world uses for exactly this job, HarfBuzz, is over a hundred thousand lines, and a from- scratch engine that handles Arabic and the Indic scripts properly is a larger piece of work than porting Jade's whole root package. It has a milestone of its own (M4), ordered so that the parts the first window needs come first and the window work is not held up by the rest.

As built in M4, part one

Points 1 to 4, 8 and 10 to 12 are built, in src/text (about 4,500 lines) with PNG in src/image. It needs no window and is in the runtime for every program, not only for Jade (D124).

The parts. face reads a font file: the table directory and collections, names, the character map (formats 4, 6, 12, 13, and 0 as a last resort; symbol fonts), widths, the line's measurements, and quadratic outlines with composites. cff runs the per-glyph programs of cubic outlines, of the plain kind (CFF ) and the variable (CFF2, with its blends). variation reads fvar, avar, gvar, HVAR and MVAR: outlines, widths and line measurements for any place on a font's axes. color paints COLR version 0 and version 1 (every paint: solid, the three gradients with their three ways of extending, transforms, glyph clips, layers, and the composite modes) with CPAL; bitmaps reads the picture formats (CBLC/CBDT, sbix) and scales them. raster is the exact-area rasteriser from the M0 spike, for quadratic and cubic curves. fonts is the list of installed fonts with matching and fallback, engine a font at a size, and system.cpp the one file written for each system. A font file is mapped into memory, not read, and a font file once used stays mapped.

What is asked of the system is the list of installed font files (on Windows, the two font folders) and nothing else: not the default font, not metrics, not a single glyph. system.cpp also holds two short lists of names per system: which families "SansSerif", "Serif" and "Monospaced" mean (Segoe UI, Times New Roman and Consolas on Windows; Segoe UI Variable is used when asked for by name), and which families to look in first for a character the chosen font lacks, before every other installed font is tried.

Matching is by family, then width, then upright or italic, then the nearest weight in the direction asked for (the order CSS uses). A family is also found by its four-style name ("Segoe UI Semibold") and by a full name. A variable font answers for every weight in its range. A bold or italic the family lacks is made up, by thickening and by slanting.

Measuring is the rule of point 8, with the clause for scaled displays as given there. Characters that only steer other characters (joiners, direction marks, variation selectors) and control characters take no room. There is no kerning and there are no ligatures, so a text's width is the sum of its characters' widths in every font.

Hinting is the M0 rule unchanged: the x-height and the capital height go to the nearest whole pixel and what lies between is stretched to fit; nothing moves sideways and nothing below the baseline moves. It is on unless a font is made without it.

To WinterWolf the engine is Fonts, Typeface, TextFont and Picture (README, "Fonts, text and pictures"), names of the engine's own. Jade's Font, FontMetrics, Color and BufferedImage are written on them in M5, and M5's canvas takes glyph pictures from the same engine into its atlas. A Picture's pixels are an ordinary bytes value.

Checked. Every glyph of every font installed on the development machine reads without a damaged result: 508 fonts, 1.8 million glyphs, 4 seconds; the variable ones at both ends of their weights too. The same for the 332 fonts that other programs on the machine carry, 300 of them with cubic outlines (the installed ones have 12). All of it also under the address sanitizer. Glyph widths of a variable font at 200 pixels agree with the ones GDI gives. The PNG reader agrees with Windows' own on 26 pictures of every kind the format has, written by Windows, and Windows reads the pictures written here. The tests hold measuring to drawing: a text drawn whole is the same picture as its characters drawn one at a time where measuring puts them, in five fonts, with fallback characters and at a scale of 1.5.

Not built, or built and not tried.

  • Cubic outlines in a variable font (CFF2) are built, and have met one font: no such font is installed here, and the one found on the machine is a test font of a single letter that the fonttools project carries. Its outlines at the places that project's own tests name come out to the coordinates those tests expect, exactly, as do those of the TrueType variable font beside it (13 axes). Neither font is in WinterWolf's tests.
  • sbix, Apple's picture format, is written to the specification and has not met a font: none is on this machine. CBDT was tried against Noto Color Emoji, which a program installed here carries, but that font is not in the tests since Windows does not have it.
  • The styles a variable font names along axes other than weight ("Sitka Display", "Bahnschrift Condensed") are not families of their own. The weight is set as asked, and the cut for the size where a font has one (its "optical size" axis).
  • Emoji stored as SVG are not read; no system's emoji font needs it.
  • The slight darkening of thin strokes that M0 suggested is left as tuning for when text is on a screen (M5).
  • Reading the names of all installed fonts takes about a tenth of a second the first time a program uses a font. If that shows at start-up, the answer is a small cache file.

As built in M5

Tier N1 is built, in src/jade (about 2,700 lines of C++) and lib/Jade (three files of WinterWolf), and the old gui library is gone with its backend, examples and test (section 3, point 4).

The parts. platform.h is the interface that is written once for each system: a window with an OpenGL context, the events it receives, cursors, the clipboard, waiting. platform_win.cpp is the one for Windows, written directly against Win32 and WGL. render draws: one shader program, shapes sent to the card as one small record each (76 bytes) and drawn instanced, the two glyph atlases (coverage, and colour for emoji), and surfaces. api.cpp is the built-in __jade, where layout units become device pixels. In lib/Jade: Native.ww (NativeWindow, Surface, NativeCanvas, Native), Input.ww (RawInput, KeyCode, PointerButton, Modifiers, CursorKind, CursorMode, ported from JadeUI's own types) and Awt.ww (the JDK's names).

Where it differs from what this section said.

  • One OpenGL context, not one for each window. A single context is made current on whichever window is being shown; every window has the same pixel format. The effect is the one the share group was for (textures and the glyph atlas are common to all windows) with less to keep in step, and the framebuffers and the vertex state, which a share group does not share, exist once.
  • Everything is drawn into surfaces; a window is shown by copying its surface to the screen. Nothing is drawn straight to a window. That is what makes the picture with no window the same picture, and the window's retained picture comes for free.
  • Clipping is done in the shader, from a clip rectangle that travels with each shape, not with the scissor rectangle. A thousand widgets each with a clip of its own are still one batch; the scissor would have ended the batch at every widget.
  • Colours are kept multiplied by their alpha on every surface, which is what lets one surface be drawn onto another correctly. They are divided again when a surface is read.
  • Polygons are rasterised by the text engine into the glyph atlas and kept by shape, so the arrows and marks a toolkit draws again and again cost one quad each after the first.
  • Layout units become pixels at one place, api.cpp: a position is multiplied by the scale and rounded, so that at 150% the edges of rectangles and straight lines are still on pixel edges and neighbours still meet. Text is drawn with the font made for that scale, by the rule of section 4, point 8.
  • The window's events come through the runtime's own event loop (VM::loopPump, loopWait): there is no second loop, a showing window keeps the program going the way a pending timer does, and while Windows runs its own loop (an edge being dragged) a timer keeps the program's tasks going.
  • A surface is collected. A new kind of value, a resource, tells the native layer when the collector finds it unreachable; the surface is then deleted from the drawing thread. What a surface takes on the card counts towards the next collection.
  • BufferedImage is in two places, memory and the card, each brought up to date from the other when it is asked for after the other changed. Its createGraphics() comes with tier N3; until then canvas() gives the toolkit's canvas on it.
  • The libraries that come with WinterWolf may use the hidden built-ins (__jade, __text): the rule that kept them to the standard library now lets in the lib folder beside ww.exe, and nothing else.

To be known when porting. As the key of a map, a Color, a Font or a Rectangle is itself and not its value: the one such map in JadeUI's root package, the cache of font metrics, is keyed by a string here. Font.deriveFont(12f) is written deriveFont(12.0): a whole number is a style and a decimal a size, which is how Java tells them apart too.

Checked. Not tried, or not there.

  • A second screen of another density, the locked pointer under a real mouse, and files dropped from Explorer: the code is there and nobody has done it.
  • Dragging a window by hand was the first thing tried once the examples were built, and it hung them: while Windows runs its own loop for a drag, the program's timers are run from a timer inside it, and that ran "whatever is due", which for an animation whose frame takes longer than its period is for ever. It now runs for a moment at a time (VM::runEventLoop with a budget) and gives Windows its turn back. A test puts a window into that state with a frame always due and requires a close request to arrive meanwhile; it fails with the old code. The test and the scripts here say the drag has begun by posting the message Windows sends; the drag loop itself is entered only by a real mouse.
  • Any graphics driver but this machine's (an NVIDIA card). Intel graphics, virtual machines and Remote Desktop are the risk section 9 names, and still are.
  • Scripted answers for file dialogs wait for the dialogs themselves (tier N2).
  • No test shows a window: the suite runs unattended, three ways, under the sanitizer, and should not put windows on the screen of whoever is at the machine.

Testing support belongs in N1 from the start: hidden windows that render to an offscreen surface, synthetic raw events fed through the same path as real ones, an in-memory clipboard and scripted file-dialog answers. That is the equivalent of the hidden test mode in the Kotlin GLFW backend, under names of Jade's own, and it is what lets the Kotlin tests be ported.

Enums. An enum is a type with a fixed set of values:

enum Way { up, down, left, right }

var t : Way = up        // t can only be one of the four, so the name is enough
t = down
if t == left { ... }
t = Way.right           // the full name is always allowed
  • Declared with enum Name { ... } and no other way. Kotlin writes enum class, because there enum is a modifier on a class; the porter deletes the word class from each declaration (22 in the library).
  • Entries have name and ordinal, the enum has entries, and an enum may declare fields and methods, as in Kotlin.
  • A bare entry name is allowed wherever the destination is declared as that enum, because there it can mean nothing else. The destinations are: a variable or field of that type, being initialised or assigned; a parameter of that type, receiving an argument; a function returning that type; and the other side of ==, != or a when branch against a value of that type.
  • Where the compiler can see the destination's type, it settles this when the program is compiled, and a name that is not an entry of that enum is a compile error. Where it cannot, typically an argument to a method (cell(c, fill = horizontal): which cell is only known when the call happens), the name is settled as the value arrives at the typed parameter, and a wrong one is an error there.
  • With no enum-typed destination the full name is required. val x = up, print(up) and items.add(up) are errors that ask for Way.up. This is what keeps a misspelt or undeclared variable from quietly turning into an enum entry.
  • The destination decides, not the name, so it does not matter that several enums share an entry. That matters for Jade: its 18 public enums have 180 entry names and 23 of them belong to more than one enum (Kotlin's LEFT, here left, is in six: Key, KeyCode, PointerButton, FloatSide, ProseEdge, SheetAlign).
  • A bare name is tried as an entry last, after locals, the object's members, the class's statics and globals. A variable called left therefore still means the variable.

Ported Kotlin always writes the full name (Fill.HORIZONTAL, here Fill.horizontal) and is unaffected. The three apps and the examples do so 321 times, about two thirds of them for Anchor and Fill in grid layouts, where cell(label("Name:"), fill = horizontal, anchor = west) now reads as well.

Namespaces. Today every file shares one set of global names, and declaring a class or a function under a name that already exists replaces it without a word, for every file. An app that declared its own Button after importing a toolkit broke the toolkit's button(...) factory from the inside. With the Jade prefix gone, Jade alone brings in about 220 short names (Button, Table, Event, Window, Block). So names get the structure Kotlin gives them:

  • A folder is a namespace, as a package is in Kotlin. The files of one folder see each other's top-level names. Nothing outside the folder sees them unless it imports the folder.
  • import Jade makes the folder's names available as Jade.Name, and nothing more: everything used from it is written with Jade. in front. import Jade.* also lets them be written bare, which is what a ported Kotlin file wants (its import com.jadelib.ui.*). Either way the names are the ones the importing file may see: public, plus internal when it is in the same library, never private. A sub-folder is import Jade.Chart (then Jade.Chart.Axis) or import Jade.Chart.*. A path that is not made of plain names is written in quotes, import "../shared/util" as util. An import is not passed on: importing a folder does not give you what that folder imported. A sub-folder is a namespace of its own and imports its parent like anyone else, as com.jadelib.ui.chart imports com.jadelib.ui.
  • Three levels of visibility, Kotlin's own. private at the top level of a file is seen in that file only. internal is seen throughout its library (Jade and all its sub-folders) and nowhere else. Anything else is public.
  • A folder's own names win over imported ones. JadeGen's TextField and Jade's then coexist, and Jade keeps using its own whatever the app declares.
  • A hidden name is reached through the import's name: Jade.Block, or Ui.Block after import Jade.* as Ui. Snips needs this: it has a Block of its own and uses Jade's in 8 places.
  • Two imports that export the same name are fine until the name is used unqualified; that use is a compile error asking which is meant (Jade.title or text.title).
  • Declaring a name twice in one namespace is a compile error, never a silent replacement.
  • Built-in names (print, Math, File, the types) are visible everywhere.
  • All of this is settled when a program is compiled; a name still costs a slot lookup at run time, as now.

What it gives the port: JadeUI's 17 packages become 17 folders with their private and internal helpers intact; JadeMem and JadeGen are one folder each; Snips' 15 packages become 15 folders, which also resolves the four names it declares twice (Tok, Expr, Stmt, Closure). A Kotlin file's list of imports becomes one line per package it uses.

How files are loaded:

  • Importing a folder loads every .ww file directly in it, once, as one unit, so its files see each other whatever order they are in. This is what import Jade does.
  • Importing a file loads that file only, into the namespace of the folder it is in. A script with import helpers beside it shares names with helpers.ww exactly as today, and the other scripts in that folder are not touched.

Static members. Kotlin has no static; what belongs to a class rather than to one object goes in a companion object { ... } inside it. JadeUI and the three apps have 111 of them. None implements an interface, has a name or is passed around as a value: every one is a plain holder of constants and functions. WinterWolf therefore gets statics, not companions, in a form that takes a companion's body as it stands:

class Grid {
  static {
    val maxTrack = 100000
    fun key(row : int, col : int) : int => row * maxTrack + col
  }

  fun add(component, row, col) { ... key(row, col) ... }
}
  • static { ... } holds declarations only: val, var, fun, get, set. Everything in it is a static member of the class. It is not a block of statements that runs once, which is what static { } means in Java and C#; initial values already run once, in order, when the class is defined.
  • The prefix stays as shorthand for a single member: static fun unit() => ..., and now also static val and static var. The block and the prefix mean the same thing, and existing static fun code is unaffected.
  • Static fields are typed and val is enforced, like any other field.
  • private static { ... } covers a whole block; 33 of the 111 companions are private.
  • From outside, a static is reached through the class: Grid.key(1, 2), Font.bold.
  • From inside the class it is reached by its bare name, both from other statics and from the class's instance methods, as Kotlin code does. That needs unqualified names in a class to be looked up as: locals, then the object's members, then the class's statics, then globals, which is the implicit-this rule in the table above.

Porting a companion is then one edit: companion object { becomes static {.

return in a lambda. WinterWolf follows Kotlin's rule, which has three cases:

fun find(id) {
  for child in children { child.find(id)?.let { return it } }    // leaves find()
  return null
}

items.forEach { if it.hidden { return@forEach }; show(it) }      // leaves the lambda, like continue

val area = fun(w, h) { return w * h }                            // leaves the anonymous function
  • In a lambda literal given to let, also, apply, run or takeIf, a bare return leaves the enclosing function. The compiler expands these five in place, so there is no call to return through: it is an ordinary return. Of the 161 bare returns counted in one-line lambdas across the library and the apps, 147 are of this kind.
  • In any other lambda literal a bare return is a compile error that points to return@label. Kotlin permits it there only when the receiving function is inline, which WinterWolf has no notion of; the porter turns those few (a forEach with an early exit) into a for loop.
  • return@label leaves just the lambda, with a value if one is given. The label is the name of the function the lambda is passed to, or one written before the lambda (name@ { ... }).
  • fun(x) { ... } is unchanged: return leaves that function, as in a Kotlin anonymous function.
  • The five names are special in one form only: a call with a lone lambda literal, x.run { ... }. The compiler has to decide what that means without knowing what x is, so in that form it is always the scope function. Classes may still declare methods with these names and call them with ordinary arguments: panel.apply(item), stepper.run(block). The library and the apps declare 25 such methods (run and apply), and all but two are unaffected. The two take a lone lambda and are called as x.run { ... }, which WinterWolf would read as the scope function: FxThread.run(block) in JadeMem and SnippyRunner.run(body) in Snips. The porter renames them or calls them with parentheses.

Strings. Today length, indexing, slice and indexOf count UTF-8 bytes while a for loop steps by character: "naïve café" has a length of 12, loops 10 times, and slice(0, 3) cuts ï in half. From now on a string is a sequence of characters, where a character is one Unicode code point:

  • length, s[i], slice, substring, indexOf and every other position count characters. "naïve café".length is 10, and a slice can never cut a character in half. A caret is an index, and caret + 1, text[i - 1] and text.substring(0, caret) in ported code are correct as written.
  • s[i] and a for loop give one character at a time, as a one-character string, so for c in s loops s.length times.
  • Where it differs from Kotlin: a character outside the basic plane, mainly emoji, is two units to Kotlin (a surrogate pair) and one character to WinterWolf. Ordinary index arithmetic is the better for it, since it can no longer land between the two halves. Code that handles the halves by hand is rewritten: 5 places in the library, all in the HTML entity decoder, and 27 in Snips.
  • A character made of several code points (a letter with a separate combining accent, a flag) still counts as several. JadeUI does not handle those either.
  • Strings stay UTF-8 inside the runtime, so the rest of the C++ code is untouched. A string that is all ASCII, which is most of them, indexes as fast as today; one with other characters gets a small table from character position to byte position, built the first time it is indexed.
  • upper and lower (and Kotlin's uppercase / lowercase) handle all letters, not only ASCII.

For ASCII text nothing a program can observe changes. For other text every position does.

Bytes. A string no longer doubles as a buffer of bytes, so binary data gets a type of its own, bytes, standing where Kotlin has ByteArray:

  • Fixed length, changeable elements: bytes(16) makes sixteen zeros, bytes([1, 2, 255]) copies a list, b[i] reads and writes, b.size, b.slice(from, to), + joins two.
  • To and from text, with the encoding named: "héllo".toBytes() (UTF-8 by default) and b.decodeToString().
  • Wherever data is not text: File(path).readBytes() and writeBytes(b), pipes and sockets (5.5), picture data on the clipboard, the hex view, image encoding and decoding.
  • In a type annotation it is bytes, lowercase like the other built-in types; the porter rewrites ByteArray.
  • An element is a number from 0 to 255. Storing anything outside that range is an error. A Kotlin Byte runs from -128 to 127, so this is one more entry for 5.3.

As built in M2 (2026-10-12). What was settled while building it, and what is left to the porter:

  • Where the library lives. What WinterWolf code can do for itself is written in WinterWolf, as extension functions and classes in src/std/*.ww, packed into ww.exe and loaded before every program: the collection and string helpers, Set, Deck (Deque until D183), StringBuilder, File. They run as fast as the native ones (a forEach over a million items takes what the native each takes), and unlike a native method that calls back into a lambda they will be able to suspend (5.5). Native are the methods called most (add, first, get, coerceIn), and what WinterWolf cannot do: reading files, format, telling letters from digits.
  • Map keys. A list, a range, bytes and a data object are keys by what they hold; any other object is a key as itself. That settles the question left open above: a list may be a key, and an equal list finds the entry. A set tells its items apart the same way.
  • A lambda after a call goes to the last parameter and the parameters between take their defaults, for methods and extension functions as for functions (joinToString { it.name }). One exception lets a function parameter be followed by optional ones, which Kotlin does with overloads: if every parameter that has to be given is there but the last of them, the lambda is that one (groupBy { key }, groupBy({ key }) { value }).
  • Named arguments to built-in methods, for the ones Kotlin code names: contains(x, ignoreCase = true), indexOf(x, startIndex = n), padStart(length = 3).
  • size, keys, values, entries, indices, lastIndex, first/last of a range, absoluteValue, sign and code are read without brackets. keys, values and entries are lists made on the spot, not views: map.keys.removeAll { ... } and map.values.remove(x) change nothing and the porter rewrites them.
  • put and remove on a map give the value that was there, as in Kotlin (remove gave true or false before).
  • orEmpty() on null is an error, because strings, lists and maps each have one and null does not say which is meant. The porter writes x ?: "" or x ?: []. isNullOrEmpty() is one function for all of them.
  • One whole-number type. Int.maxValue is Kotlin's 2147483647 so that a limit means the same number, but arithmetic goes on past it instead of wrapping. toLong is toInt.
  • Constants are camelCase here too: Math.pi, Int.maxValue.
  • File reads and writes a whole file at a time, on the calling thread. Reading in pieces and not blocking come with 5.5.
  • Upper and lower case, and which characters are letters, digits and spaces, come from Windows for characters outside ASCII until the text engine brings its own tables (M4).
  • The math functions stay in Math (decided 2026-10-12): there is no bare min, max, abs or sqrt. The porter writes Math.min(a, b) for Kotlin's min(a, b), and so on for the rest of kotlin.math (or minOf, maxOf, absoluteValue).
  • Left to the porter, because the names would not be WinterWolf's: println is print and Kotlin's print is write; arrays are lists (IntArray(n) is List(n) { 0 }); a Comparator is a function of two values; filterIsInstance<T>() is filter { it is T }; a sequence is a list; and the bit operations shl, and, xor are the operators <<, &, ^.
  • Regex is still to come (N5).
  • A compiled .wwc now carries the WinterWolf-written library, about 85 KB, where it was a few hundred bytes for a small program. A built .exe is 0.18 MB larger than before.

5.5 Threads and async I/O

WinterWolf has neither today. JadeUI itself barely needs them: one UI thread does everything and the core starts a single background thread, to index a large text file. The apps are the reason:

AppBackground work
JadeMemThree single-thread executors (memory sampling, pool attribution, disk scan), with results handed to the UI thread.
JadeGenA child Python process spoken to over pipes and a socket with reader threads, and threads for long jobs.
SnipsA thread accepting connections from a second launch of the app, and a thread pool running its evaluator.

What is added, in dependency order:

  1. Execution contexts. The VM is split into what is shared (objects, globals, interned strings, the collector) and what belongs to one line of execution (value stack, call frames, error handlers, open upvalues, native temporaries). Threads, suspending functions and workers all stand on this.

  2. Threads. Real operating-system threads sharing one heap, with one of them running WinterWolf code at a time. They switch at the points where the collector may already run (calls and loop back-edges) and whenever one blocks in native code. So:

    • objects are shared between threads as in Kotlin, and thread code ports as written;
    • a race can give a wrong answer but cannot corrupt memory or crash the VM;
    • WinterWolf code does not run faster on several cores. The parallelism is in native work that runs outside the lock: I/O, system calls, image decoding.

    Surface: Thread(function, name) with start(), join() and isDaemon; Thread.sleep(ms); a lock, with synchronized(lock) { ... }; a blocking queue; a small executor (one thread, or a pool), since two of the apps are built on them, whose tasks give back a future that can be waited on with a time limit and cancelled; and an interrupt flag a running thread can check (Thread.isInterrupted), which is how Snips stops a script that overruns. @Volatile is an error saying it is not needed (L47, D153).

  3. The event loop. One per process, and the same loop that delivers window events: timers, plus a post(task) that is safe from any thread. A console program has it too and ends when its script has finished, no non-daemon thread is running and the loop has nothing left.

  4. Suspending functions. A function can set itself aside in the middle of a call and be taken up again later, where it was, without holding a thread. This is Kotlin's suspend fun, and it follows Kotlin's model, not the async / await of JavaScript and Python:

    • A suspending function is called like any other. There is no keyword at the call. suspend on a declaration is accepted and documents intent; any function may suspend when it runs inside a flow.
    • Underneath, each flow runs on a small stack of its own (a fiber), which is why it can pause several calls deep.
    • Two primitives, under Kotlin's names: start a flow (startCoroutine), and suspendCoroutine { c -> ... }, which sets the flow aside until c.resume(value) is called, on whichever thread calls it.

    The reason is Snips. Jade's dialogs are modeless and answer through a callback, and Snips wraps them so that a command asking several things reads top to bottom: 23 suspend functions, 149 calls to them, 55 flows started, built on those two primitives and nothing else. It ports as written. With await at every call it would not, and with callbacks alone the 55 flows become nested callbacks.

  5. I/O. Files, child processes with their pipes and exit code, TCP sockets (connect and listen), and fetching a URL. There is one set of functions, written as ordinary calls:

    • Called on a background thread, a read or a write blocks that thread. That is how the apps do all their I/O today (JadeGen's reader threads loop on readLine), and it ports as written.
    • Called inside a flow on the UI thread, the same call sets the flow aside until the data is there, and the window stays live. This is the async I/O: no second set of functions and no callbacks.
    • Called on the UI thread outside a flow, it blocks the UI, as it would in Kotlin.

    Underneath, worker threads make the blocking calls.

  6. Isolated workers. A worker is a second WinterWolf VM on its own thread, with its own heap and its own lock. It shares nothing with the program that started it; the two exchange messages, which are copied. Workers are what threads are not:

    • WinterWolf code in a worker really runs on another core, at the same time as the main program.
    • A worker can be killed outright, however stuck it is, because nothing else depends on its memory.

    A worker is started from a file or folder of code that it loads itself, not from a function: a closure cannot cross, since everything it refers to lives in the other heap. A message can hold numbers, strings, booleans, null, bytes, and lists and maps of those. Surface: Worker(path), post(message), a handler for messages coming back (delivered on the event loop), terminate().

    Threads come first, since the apps' code is written for them. Workers stand on the same execution contexts and are added after: none of the three apps needs them to port, and the first real use would be Snips' evaluator, which is self-contained, takes values and returns a value, and wants a hard kill for a script that never reaches a checkpoint.

  7. Parallel sections (added 2026-10-13; milestone M3.5). Several cores running WinterWolf code on the same objects at the same time, for the one shape of work where that is safe: many items, each worked on by itself.

    balls.parallelStream().forEach { it.move(width, height, steps) }
val totals = orders.parallelStream().map { priceOf(it) }.toList()

    Threads take turns and workers copy; this does neither. The items are dealt out to the cores, and for the length of the section the runtime holds each core to what the program is promising:

    • A core owns the items it was dealt, and whatever those items alone hold, and whatever it creates. It may change those.
    • Everything else can be read and not changed: the variables the lambda sees, other objects, globals. A write to something the core does not own is an error that names it, raised there. It is never a damaged list or a crash. So { it.move() } runs on every core, and { it.move(); moved.add(it) } is refused the first time it runs.
    • A result comes back by being returned: map, filter, sumOf, count, any, all, minOf, maxOf put the cores' answers together on the calling thread.
    • Numbers in bulk are shared by slice. bytes, and a buffer of numbers to be added with it, can be dealt out in pieces that do not overlap, each owned by one core. That is what filling the points of a picture for the graphics card needs, or painting a picture band by band.
    • Inside a section there is no waiting: no lock, no I/O, no setting a flow aside. Those are errors there. The section itself is an ordinary call that returns when every core has finished, with the first error if there was one.

    What it takes underneath: the interpreter's working state, which exists once today and is handed from thread to thread, becomes one per core; objects made in a section are kept on the core's own list and joined to the rest at the end, and the collector waits for the end; every instruction that writes to an object asks who owns it, which costs nothing outside a section and one comparison inside; and each built-in function is marked as safe to run on several cores or not, the rest being errors in a section.

    What it is not for: work that is quick for each item and few in number is faster left alone, since starting the cores has a cost. And it does not draw. Moving the 5000 balls of the example is 0.6 ms of a 26 ms frame; the rest is the old library drawing circles one call at a time, which no core can share. In Jade the graphics card draws them all in one call, and what the cores are for is working out the numbers it is given.

    As built in M3.5 (2026-10-13). What was settled while building it, and where it differs from the above:

    • No change to the interpreter. "One interpreter state per core" turned out not to need the state taken out of the VM. Each core has a VM of its own, made once and kept, with its own stack and calls; these VMs work on the heap of the VM that started the section, which waits with its lock held so that none of its threads runs. A core's VM has a copy of the table of variables, which it reads and never writes, and uses the root's table of names.
    • Ownership is one byte in every object: 0 for shared, otherwise the core that owns it. Every place that looks into an object asks: the property and index instructions, method calls, loops, comparing and printing, the keys of maps, and every built-in method as it is called, with those that change what they are called on marked as such. Outside a section the question costs one comparison that never fails.
    • A core owns the item, not what the item holds. "Whatever those items alone hold" cannot be told without walking the whole heap, so what an item holds is shared: it can be read, and replaced by something the core has made, but not changed in place. An item that is itself a list or a map is owned like any other.
    • Another core's item cannot even be read, since its owner may be half way through changing it. Asking whether two values are the same object is allowed, so a core can find its item in a list of everyone's.
    • The same object twice in one stream is an error, as it would be two cores' at once.
    • The buffer of numbers is not built. bytes is shared out by position (parallelChunks); a buffer of floating-point numbers is added when Jade has points to hand the graphics card (M5).
    • Built-in functions that wait, or that work on what the program has one of, are refused in a section by name: threads and locks, the event loop, flows, files and streams, workers, windows, input and exit.
    • Measured on a machine with 24 cores: moving 50,000 balls 7.4 ms in one loop and 0.9 ms in a section; 64 counts of primes 2084 ms and 129 ms. Starting the cores costs 0.04 ms, so a section pays from about 300 quick items. Dealing the items out and taking them back is done by the one waiting thread, which is what keeps quick items from gaining more.
    • The bounce example is one line different (gui_bounce_parallel.ww) and, as foreseen, no smoother: 37 frames a second at 5000 balls either way.
    • The stress setting named in the milestone was a mistake: running every forEach of the library as a section would refuse the many lambdas that change a variable, as it should. Instead WW_CORES sets the number of cores, and the section tests are run with 1, 2, 3, 7 and all of them, under the sanitizer.
    • What there is no tool for: nothing on Windows finds two cores touching the same memory, so the rule was checked by going through every instruction and every built-in that writes. All writes are either checked or made to an object just created.

Rules for Jade, the same as JadeUI's:

  • The tree, layout, painting and events belong to the UI thread, the one running the loop.
  • Safe from any thread: every member of Window, Jade.requestRepaint(), Jade.requestFrame() and Jade.scheduler, which with a delay of 0 is how a background thread hands a result to the UI.
  • Anything else called from another thread raises an error naming the thread and the call. Kotlin lets such a call through silently; here a porting mistake shows at once.
  • Inside Jade, the large-text view keeps its indexing thread, and file dialogs and image decoding run on native workers.

Tested as the collector is: a stress setting that switches threads at every safe point, run over the whole suite.

As built in M3 (2026-10-13). All six points: workers (point 6) were planned for M10 and were brought forward. What was settled while building it:

  • Execution contexts. A Context holds one line of execution: its value stack, its calls and their catch blocks. Each thread has one and each flow has one. The interpreter keeps working through members of the VM, as before, and a context's state is moved in and out when it starts and stops running, so the instruction loop is no slower for it.
  • The lock. One thread runs WinterWolf code at a time. A thread that has waited 5 ms asks the one running to give way, which it does at its next safe point; a thread that blocks lets go at once. WW_THREAD_STRESS=1 changes threads at every safe point. A list or a map is never seen half changed, and the Atomic... classes need no lock of their own: a method with no call in it runs in one piece.
  • Flows have no thread and no stack of the machine's: a flow is a context, and setting it aside means leaving the instruction loop with its calls still in place. So a flow cannot be set aside from inside a built-in function that has called back into the program, as this plan foresaw. To leave few such places:
    • every method of a list, map, string or range that takes a function is now written in WinterWolf, map, filter, each, find, reduce, first { } and forEach included;
    • apply, run, also, let and with set the block going as a call of the program's own instead of calling it from inside themselves;
    • what is left is the comparison function of sort, a property's getter, toString() when something is printed, == when a collection compares its items, iterator(), and the initial values of fields. A flow that tries to wait there gets an error saying so.
  • Kotlin's coroutine names, and nothing above them: startCoroutine (as a method of a function, and as a function taking the lambda), suspendCoroutine, Continuation, Result, EmptyCoroutineContext, runCatching. Snips' Flows.kt ports line for line, and is in the tests in that form. suspend is accepted in front of fun and in a function type. Added on top: delay(ms) and future.await().
  • Where a flow goes on. On whichever thread resumes it, there and then, as in Kotlin without a dispatcher. What the runtime itself resumes (the end of a read, a delay, an awaited future) it resumes on the main thread, from the event loop.
  • One event loop, the EventLoop object: post, after, every, run, isLoopThread. It starts when the script ends. In M5 the window's messages are waited for in the same place the loop waits now, so there is one loop and not two.
  • Errors nothing catches. In the script or in a task of the loop: the program ends, with the report and exit code it had before. On another thread: that thread ends, with the report, and the program goes on, as in Kotlin. In a flow: the error goes to whoever was running it, unless it was started with a completion.
  • One set of I/O functions (VM::blocking): on a thread the call blocks with the lock released; in a flow on the main thread a worker thread does the waiting and the flow is set aside. File's whole-file calls go the same way, and a file can now also be read and written a piece at a time.
  • Java's names for threads and I/O, since that is what the apps are written in: Thread, synchronized, Executors, Future, CountDownLatch, AtomicInteger, ProcessBuilder, Process, Socket, ServerSocket, InputStream, OutputStream, IOException, InterruptedException, TimeoutException. Where they differ:
    • Future is also what Kotlin code calls CompletableFuture (it has complete);
    • a stream reads and writes text itself, so bufferedReader() and bufferedWriter() give the stream back;
    • wait, notify and notifyAll are methods of Lock, not of every object, though any object can be the lock of a synchronized;
    • a time limit is a number and a TimeUnit, with its names in camelCase (TimeUnit.seconds), and milliseconds when no unit is given;
    • LinkedBlockingQueue is BlockingQueue; ConcurrentHashMap and the synchronized collections are plain maps, lists and sets, which the lock already keeps whole.
  • @Volatile is an error saying it is not needed (L47), as are Kotlin's other annotations for the JVM, each saying what to write (@Synchronized a lock, D153).
  • return inside synchronized { } is return@synchronized, because it is a call and not expanded in place as let is. If the apps turn out to return from it often, it can be expanded in place too.
  • For a program to talk to a copy of itself, as Snips does for a second launch: Process.currentCommand() is what started it. flush() sends on what has been printed, which matters when another program is reading it.
  • Workers as point 6 describes them, with these particulars:
    • the script is named by a string in the call (Worker("physics.ww")) and compiled into the program there, as a module with names of its own, so that a built executable carries its workers; the worker loads its own copy of the whole program and runs that one module;
    • in the worker, the program that started it is Worker.parent (onMessage, post, close);
    • terminate() stops the worker at its next safe point, not by killing its thread: the two runtimes share the process's memory allocator, and a thread killed inside it would take the program with it. A worker stuck inside one built-in call is not stopped until the call returns;
    • a worker is a daemon or not, like a thread; it has no windows;
    • measured: four workers do four jobs in the time one takes, and a message of 25,000 numbers takes about 0.3 ms each way.
  • The old gui library's App.run() now waits with the lock released and runs this loop inside its own, so threads, workers and EventLoop work in a program with a window. That is the shape M5 gives Jade's loop.
  • Not built: fetching a URL (point 5 names it; the milestone does not, and none of the three apps' background work in the table above needs it); the three I/O kinds are on Windows only.
  • What it cost: map and filter now run WinterWolf code instead of C++ and are slower for it (over a million items, map takes 40 ms where it took 26, filter 39 where it took 31); a plain loop and everything else are as fast as before. An error inside the lambda shows one more line in its trace, the library function's.

5.7 Static types (M6.5)

Added after M6, at the user's decision (2026-10-13 and 14): WinterWolf becomes statically typed, as Kotlin is. Until now a variable or parameter without a written type held anything, a written type was checked only when the line ran, and obj.name was looked up by name with nothing known in advance. The point is to find mistakes when compiling (a wrong argument, a member that does not exist, box.secret from outside Box), and the Kotlin apps being ported carry every type already.

Settled by the user.

  • A variable takes its type from its initial value: var a = 5 is an int, val box = Box() a Box. A written type still wins (var n : number = 0).
  • var sum = 0 then sum += 0.5 is an error, as in Kotlin. number stays, for a value that may be either.
  • Two integer types, byte (0 to 255) and int (64 bits), decided as D19 (L0 in language-choices.html).
  • A variable or field that starts as null needs its type written: var parent : Component? = null.
  • Every parameter has a written type, by class or interface: fun adopt(child : Component). A parameter without one is an error. The same goes for a class header's entries.
  • any is the type of anything; its fields and methods cannot be used until it is cast (x as Box), or tested (if (x is Box) { x.secret }).
  • Generics: typed collections (list<int>, map<string, Component>, set<T>), function types ((int) -> bool, Grid.() -> unit), and the program's own generic classes and functions (class Box<T>(val item : T), fun <T> first(items : list<T>) : T).
  • No final. The compiler sees the whole program and every override, which is all final would tell it; override already keeps a method from being replaced by accident. open and final are not keywords: either one in front of a declaration is an error.
  • The name of a function is never given another value (2026-10-18, D159), as in Kotlin: area = { ... } for a fun area is a compile error saying to keep a function that changes in a var of a function type. A call of a function then gives what the function declares, which lets the compiler leave out checks it has proved.
  • Generic types are kept when the program runs, as in C# and unlike Kotlin and Java (which drop them for compatibility with code compiled before generics, a reason WinterWolf does not have). A collection knows what it was made to hold (items.itemType, map.keyType, map.valueType), so does an object of a generic class of the program's own, and x is list<int> and x as list<int> are checked in full. A generic function is given its type arguments as hidden arguments, which is the one cost: about that of one more argument per call. A collection made where its type is known costs nothing more, and reading, iterating and adding re-check nothing. (Kotlin code that makes a wrong unchecked cast fails at the cast here, where on the JVM it fails later or not at all.)

Proposed here, to be confirmed or changed when M6.5 is shown.

  • Return types are worked out from the body when not written, from => value and from the returns of a block. A function that calls itself writes its return type. (Kotlin takes a block without one to return nothing; this asks less of ported code and of the library.)
  • Lambdas take their parameter types from where they are passed: items.map { it.name } needs nothing written. A lambda with nowhere to take them from writes them, { x : int -> x + 1 }.
  • Narrowing: after x is Box, x != null, x ?: return and the like, a local variable, a parameter, or a val of this has the narrower type for as long as the test holds, as Kotlin's smart casts.
  • Collections are read-only unless marked open (D32, built in M6.6; M6.5 has one list type): a list<Button> can be passed as a list<Component>, which may only be read through that name; an open list<Component> may also be changed and takes only a list of exactly that type, since a Label could otherwise be added to the buttons. Maps and sets alike; frozenList, frozenMap and frozenSet are what nobody may change (D26). A list literal takes its element type from where it goes (show([ok, cancel]) with show(items : list<Component>)) or, with nowhere, from what its items have in common.
  • Overloading by parameter types comes with it. Section 5.6 merged JadeUI's overloaded names into one function that looks at its argument; with every parameter typed that function would have to take any, so overloads are allowed instead, chosen when compiling, and API names stay as they are.
  • Built-in functions (written in C++) get their types from declarations written in WinterWolf (external fun print(vararg items : any), external fun string.substring(start : int, end : int) : string), kept with the standard library.
  • Types are checked when compiling. The checks the VM makes today for written types are left out wherever the compiler has already proved them, so running costs nothing more and typed code runs a little faster. Compiling takes longer, which matters only when running from source.

Built in five parts, each tested, the language working throughout. The checker first runs beside the old rules and is switched on for good at the end, when every line of WinterWolf in the repository has its types.

  1. The checker's core. Written types read in full (type arguments, function types, receivers); a type checker as a pass of its own between parsing and compiling, which knows every class, interface, field and method of the whole program; inference of variables; operators; calls to declared functions, methods and constructors (count, names, defaults, types); members on known types; any and casts; null and ?., ?:, !!. The type nothing for jumps and functions that never return (D61), and and, or, ! and conditions taking only bool (D62). Run with ww check, and by the tests, without stopping other programs.
  2. Generics and lambdas. Type parameters on classes and functions, with bounds (<T : Comparable>); inference of type arguments; function types and lambdas with and without receivers; extension functions; narrowing; when; destructuring; overloads.
  3. Everything typed. The case of type names first (D154): List, Map, Set, Bytes, Sequence and the frozen types Title case, a fixed set lowercase, so every type below is written once. Declarations for the built-in functions, with their parameter names so that any argument can be named (D116); the standard library (3,683 lines) with generics, its functions that relied on a trailing lambda filling the last required parameter made overloads (D56); Jade (3,757 lines), its types taken from JadeUI's Kotlin; the examples; the 117 test files (9,698 lines); the README. Then the rule is switched on: a parameter without a type, or code the checker refuses, is a compile error. (On since step 5: what the checker finds stops the program, all of it listed; a variable or field with neither a type nor a value is an error too, as D18 implies and Kotlin does.)
  4. Using the types when running. The run-time checks the compiler has proved go; member access on a known class looked up by position where that is safe. An anonymous object's class compiled once instead of on every evaluation, its captured vals copied into hidden fields of the object and each captured var kept in a small shared box, as Kotlin does on the JVM (today each object : Shape { ... } rebuilds its class and method closures: about 560 ns against 165 for a data object). Inline caches where a member cannot be found by position (calls through an interface, on a union or an any): each call site remembers where the member was last time. (Instructions chosen by type moved to M6.6 on 2026-10-18, to come with generic types kept when running: until then a value of another type can still arrive through an erased generic or a built-in function, and the test is what catches it; leaving the tests out of the numeric loop measured only 1.3% faster.) The aim, measured before and after on a fixed set of benchmarks (a numeric loop, calls, field access, a JadeGate-style simulation slice): two to five times faster on typed numeric code.
  5. Smaller built programs. (a) The M0 spike (src/spike, the Spike class) out of the build; the scripts in spikes/m0 stay on the branch m0-spikes. (b) Code a program cannot reach left out of its compiled form, worked out from the types: functions, classes and methods never called (overrides of a called method in a reachable class kept, and what is found by name when running). Reflection keeps what D50 says. (c) Built programs made from ww.exe itself with what a running program never needs left out (decided 2026-10-18, D161): the code of the compiler, checker, parser, lexer, the cache and the shell is kept in a section of the executable of its own, and the standard library's source text in another, and ww build writes a copy of ww.exe without those sections' bytes (the space they took kept, empty, so that every other address stays as it was), then the program. One file, nothing in it twice, and the base never out of step with ww.exe. What both sides use (the inline functions and templates of the headers) stays in the common code: the section is chosen after a file's includes. Proved, not assumed: the build links what is kept once more on its own, which fails if it names anything left out, workers included; checks on the link maps that every function that link needs is in a section kept (a template the C++ library's own code uses may otherwise be made from a copy left out); checks that nothing left out runs as the program starts (a global of such a file is made on first use); and the tests run as programs built this way. (d) Jade's window, drawing and the text engine in a third such section, left out of a program that reaches neither Jade nor the text engine (fonts and images are in the standard library since D124, so not importing Jade is not enough). A built program reads only its own end to find its code, not the whole file. When part 5 began, print("hi") built was 2.98 MB (the executable, with 215 KB of compiled program) and ran in 11.0 ms, 4.5 of them the process itself; the widgets example 3.23 MB, with 472 KB of program. Sizes and start times measured before and after.

M6.5 ends with every test and example passing under the checker, a set of tests of the checker's own errors, the suite under the sanitizer and stress settings, the timings of part 4 and the sizes of part 5. Version 0.6.5.

6.1 Window replaces JadeHost, JadeWindow and WindowSpec

JadeUI has two window types and two ways to open one: JadeHost, the app's main window, made by constructing a host; and JadeWindow, the handle of a dialog or secondary window, made with JadeUi.windowOpener.open(WindowSpec(...)). In Jade there is one class, Window, and one way: construct it and call show().

  • Making one. 6.2 The Jade prefix is dropped, and how names are cased

Casing. Everything we build follows one rule (settled 2026-10-12):

  • Libraries and classes are in Title case: the library is Jade, a sub-folder Jade.Chart, and so is every class, enum, interface and object (Window, ListBox, Event.Click).
  • Methods, fields, variables and constants are in camelCase: openWindow, windowOpener.
  • The built-in type names are lowercase (int, string, list, ...). They are the one exception.
  • Constants and enum entries are camelCase too, JadeUI's included: Font.BOLD is Font.bold, Fill.HORIZONTAL is Fill.horizontal, MAX_TRACK is maxTrack. This is the one place where WinterWolf's names differ from Kotlin's by more than the dropped prefix. The porter's rule is mechanical (UPPER_SNAKE to camelCase) and applies to about 3,350 uses across JadeUI and the three apps. A keyword is a name wherever only a name can come, so ImageStore.CLASS becomes ImageStore.class like the rest. An entry called NAME (SortKey.NAME, and Value.NAME, T.NAME, Table.NAME in Snips) becomes name like the rest: a class tells its own name with className, so name is free on the enum, where SortKey.name is the entry and SortKey.size.name each entry's own name. Only entries cannot be the name of an entry. A member of an enum called entries, name or ordinal is an error unless it is written override and is a property of the same type as the one it replaces; anywhere else those three are ordinary names. Inside the enum super.entries, super.name and super.ordinal still give the originals. (super reaches a superclass's properties in general, not only its methods.)

The library and its global object are both called Jade. That works: Jade.Button is the library's class, and a name the library does not declare, Jade.requestRepaint(), is looked for on the object.

Jade is the one standard GUI library, so its classes do not carry its name. A class called JadeXxx in Kotlin is Xxx in WinterWolf; everything else about it is unchanged.

How a window is drawn. A request for a repaint marks the window's loop dirty and posts one task to the event loop, however many requests come before it runs; that task plans the frame (RenderLoop), lays out if it must, and paints either everything or the damaged rectangle through a clipped canvas onto the window's kept picture. A component's kept picture is a Surface at the window's scale, drawn back pixel for pixel.

Text is measured for the screen it is drawn on. JadeUI measures with a scratch image and lets Java scale the drawing. With the rule of section 4, point 8, a line is a few units wider on a dense screen than the same line measured at a scale of 1 (up to 8 for a long one at 2x), so layout that measured at 1 would cut text short. Jade.layoutScale is the scale of the window being laid out or painted, set by its host, and metrics(font) measures at it.

A gap in the language, found here and closed. private on a member was accepted and changed nothing, and inside a block that runs on an object (grid { }, row { }) a bare name is looked for among the object's members before the program's top-level names. RowScope keeps its grid in a private field called grid, which hid the function grid() from every row { } block: a grid in a grid failed. Now the access words are enforced for members: private, protected, internal, and the one in front of set under a property. A member the code may not use is not what a bare name means in a block written outside its class, so a builder can keep what it likes to itself (Grid has place, tracks, effective, occupied) without hiding a name of the program's; and object.name on such a member is an error.

How it is done: the compiler gives every class and every library a number and marks each function with the numbers of the classes it is written inside of and of its library. A class is told what it declares of each member (Op::MemberAccess, Op::StaticAccess): the name then leads to the numbers the code using it has to carry one of. For a private member that is the class that declared it, and any subclass that declared it again with private override; for a protected one the class and, added as each is made, its subclasses down to the object's own; for an internal one the library. Assigning has a mark of its own beside it, for private set. Subclasses inherit the marks. Reading, assigning or calling a member by name, with an object in front or bare in a block, is refused when the function doing it carries none of the numbers.

The cost is kept off ordinary code. A name that no class restricts is passed with one test. A member a class declares itself, reached through this by its own code, needs no check at all, and the compiler writes an instruction that makes none (GetOwn, SetOwn, InvokeOwn). Code written in the class of the object it works on, and an object whose class restricts no name like the one asked for, are passed without a lookup. Four loops of nothing but member access (no restricted members; a class's own private members; a subclass using what it inherits; a public member whose name is private in another class) run level with the build that checks nothing, within the 2% the timings scatter by. Tests: tests/member_access.ww, and for a library's side tests/jade_grid.ww.

In Jade the words are as in JadeUI where a program cannot tell the difference: Component.parent, overlayDescendants and Jade.renderGeneration have private set, and adopt, release, invalidateSizes, overlayDescendants and effectiveComponents are internal. WrappedLabel.wrap, Jade.register and Jade.registeredGrids, internal in JadeUI, are left open: JadeUI's tests are part of its module and may use them, and the tests carried over here are a program outside the library.

7. Order of work

The work goes one milestone at a time. A milestone is built, tested and shown, and the next one starts only when the result is accepted. Nothing beyond the current milestone is committed to.

  • Built: inside a milestone the work lands one feature at a time, each with its tests, as the language has been built so far. Direction can change at any point.
  • Tested: each milestone names what it ends with. That is run and reported, together with the full test suite, also under the sanitizer and the stress settings.
  • Shown: something that runs, to try by hand, with a short account of what was built, what turned out differently from this plan, and what that means for the milestones after.
  • Versioned: the version of ww goes up with each milestone: M1 is 0.1.0, M2 is 0.2.0, M3 is 0.3.0, M3.5 is 0.3.5, and so on. ww --version then says which milestone a build is.
  • Accepted, or not: the next milestone starts on a go-ahead. If the result is not good enough it is reworked first; if it changes what should come next, the plan is revised before going on.

Later milestones are described in less detail on purpose. Each is planned properly when it is reached, with what the earlier ones taught.

M0. Two spikes. Done and accepted. What they found is in plans-and-gaps.html; the code is on the branch m0-spikes. Spike 1: lambda literals, trailing lambdas and receiver blocks in the parser, to find the grammar conflicts before committing (a { after a call in an if header, and telling a map literal from a lambda by its first tokens), and the two loading questions left open under namespaces in 5.1. M12. Networking, for JadeMail, JadesDomain and JadeNet. Added 2026-10-16. Three apps that will probably be ported, all of them servers or tools on the network: JadeMail (13,400 lines: an SMTP server and deliverer, an IMAP server, DNS checks and MTA-STS), JadesDomain (6,400 lines: a DNS server over UDP and TCP, DNS over TLS and over HTTPS, an admin server, zone transfers, a forwarder) and JadeNet (3,900 lines: its own encrypted transport, tunnels, port forwarding, a netcat). Plain sockets and listening sockets exist (M3); what they also need, by their use in the code:

  • TLS, as client and server, with certificates from PKCS#12 files, and upgrading an open connection part way through (SMTP's STARTTLS): SSLContext, SSLSocket, KeyStore are used about 60 times. WinterWolf's own TLS 1.2 and 1.3 (changed 2026-10-17: some apps run as dedicated servers on Linux, and the same code must agree with itself on every system; SChannel is Windows' only, and Linux's TLS libraries are third-party code that may not be there). Split as Go's crypto/tls, rustls and Java's own TLS are:
    • The protocol in WinterWolf, most of the code: the handshake's states, building and reading its messages and extensions, the record layer's framing, the key schedule (a sequence of HKDF calls), X.509 certificates (DER) and checking their chains, alerts, session tickets and resumption, STARTTLS, PKCS#12. Reading untrusted input in WinterWolf cannot overrun a buffer or use freed memory, the kind of mistake behind the worst TLS holes (Heartbleed), so this is safer than C++ as well as easier to read and test.
    • The primitives in C++ (the cryptography below), working in place on part of a bytes (aead.seal(into = buf, at = 5, from = buf, length = n)), so a record is neither copied nor allocated: the WinterWolf code handles a record's 5-byte header and C++ encrypts the up to 16 KB behind it. Sending and receiving cost what an all-C++ TLS costs; a handshake spends a little more of the processor on reading certificates (a fraction of a millisecond, less after M6.5 to M6.7), next to the public-key work and the network's round trips, which take longer.
    • Modern suites only: key exchange by ECDHE (X25519, P-256), encryption by AEAD (AES-GCM, ChaCha20-Poly1305); no CBC and no RSA key exchange. Every comparison that must take the same time whatever the secret is then inside the C++ primitives, and the classic timing attacks on TLS (Lucky 13, Bleichenbacher) belong to the suites left out. It is what current clients and servers use. A mistake in TLS is a hole in a mail server, so it is tested against the published test data (the RFCs' vectors, NIST's, Wycheproof's: data, not code) and against real clients and servers of each kind, and fuzzed. Trusted certificates come from the system's own store: Windows' certificate store, Linux's files under /etc/ssl/certs.
  • Cryptography: hashes, signatures, X25519 key agreement, AES-GCM, HMAC, secure random numbers, for JadeNet's handshake and for jadelib-crypto, which JadeMail and JadesDomain use. WinterWolf's own, in C++, one implementation on every system (changed 2026-10-17, for the same reason as TLS): checked against the published test values, written so no secret leaks through timing, using the processor's AES and SHA instructions where it has them, and secure random numbers from the system (BCryptGenRandom on Windows, getrandom on Linux). Public, as every C++ piece is (section 1): a Crypto library of WinterWolf types any program can use (Sha256, Hmac, Hkdf, AesGcm, ChaCha20Poly1305, X25519, Ed25519, Ecdsa, Rsa, SecureRandom), each taking and filling parts of a bytes in place. The crypto is built and tested before TLS is started on it.
  • Linux for the servers (moved from M13): JadeMail, JadesDomain and JadeGate's dedicated server all run on Linux as well as Windows (the user, 2026-10-17). The runtime without windows, built with GCC or Clang, runs the same programs, and everything this milestone builds works on both: TLS and the cryptography, UDP, addresses and looking names up, the HTTP client and server, files, paths and starting other programs. Jade's windows stay Windows-only until asked for.
  • UDP: a datagram socket (DatagramSocket, DatagramPacket), for the DNS server and JadeMail's DNS client; 27 uses.
  • Addresses and DNS: an address value type for IPv4 and IPv6, a host and port, and looking a name up (InetAddress, InetSocketAddress, about 110 uses).
  • HTTP: a client (java.net.http.HttpClient, used for MTA-STS and DNS over HTTPS), and for JadesDomain a server (DNS over HTTPS, the admin pages).
  • The parts of JadeLib these apps use, ported before them: jadelib-json (all three), jadelib-crypto (JadeMail, JadesDomain) and jadelib-db (JadeMail).

Servers fit WinterWolf's model as it is: each connection is waiting most of the time, so threads that take turns, or better tasks (D81), one per connection with no thread of its own, serve them well. Ends with the three apps' own tests passing, on Windows and on Linux, and each talking to a real client of its kind (a mail program, a DNS resolver, a second JadeNet).

M14. Native code for built programs. Added 2026-10-16, placed when wanted. ww build --exe writes C++ from the whole typed program and compiles it with the system's C++ compiler (Visual Studio on the machine that builds, not on the machines that run it; a tool, as it is for building WinterWolf, not code inside the program), as Nim does. Typed code then runs close to hand-written C++, typically ten to fifty times faster than bytecode. An x64 code generator of WinterWolf's own, needing no compiler, was considered: much more work for slower code unless much is put into it. Compiling while running (as LuaJIT and V8 do) is not planned: built programs are where speed is wanted, and the VM (M6.7) serves the rest. ww code.ww keeps working as it does: it compiles the source to bytecode and runs it on the VM, with no C++ compiler needed; native code is only what ww build --exe makes, and a program behaves the same either way, which the tests check by running every test both ways.

Port the tests with the code. The root package alone has 71 test files, and most assert on recorded draw operations, which carry over. Tests that hard-code numbers derived from Java's font metrics will need new numbers: no other font engine measures text exactly as AWT does.

It is refused wherever waiting is impossible, even inside a suspend function: a sort's comparison, a getter or setter, toString, == and hashCode, a generator's block (where only yield waits, L78) and a parallel section. Call it from a suspend function, or start it in a task and use the result when it is ready: task { fetch() }.then { title = it }; and for an unmarked caller, 'load' calls 'fetch', which may wait, so 'load' may wait too: mark it 'suspend fun load()', or run the call in a task of its own: task { fetch() }. reified is an error saying why it is not needed: type arguments are kept when the program runs (L14), so x is T works in any generic function. 9. Risks

  • The language work is larger than the library's first milestone. Section 5.1 is about fifteen features; several (interfaces, lambdas with receivers, implicit this, nested classes) touch the compiler, the VM and the bytecode format.
  • Grammar conflicts. WinterWolf writes if cond { ... } without parentheses; with trailing lambdas, if ready() { ... } is ambiguous. Swift has the same problem and forbids trailing closures in conditions. Spike 1 exists to settle this early.
  • Namespaces change how every existing program is put together. Imports stop being global, so current multi-file WinterWolf code, the tests under tests/modules among it, has to be revisited, and the bytecode file and the standalone-executable bundling both carry module information that changes shape.
  • Receiver lookups cost a run-time check per unqualified name inside a builder block, and Kotlin lets a receiver's member hide a top-level function of the same name (label).
  • OpenGL and a text engine of Jade's own make the native layer much bigger. Smooth shapes, a font reader, a rasteriser, hinting, the glyph atlas and font lookup all have to exist before the first label appears, where a ready-made 2D library would have supplied them.
  • The text engine is now one of the largest pieces of the whole plan. Shaping for every script, text direction and the Unicode data are what a hundred-thousand-line library exists to do, and writing them from scratch is more work than porting Jade's root package. It is also work that none of the three apps needs in order to run: their text is Latin. It is in the plan because the engine is meant to be complete, and it is ordered (M4, part two) so that it cannot delay the first window.
  • Small text looking good enough was the question the M0 spike was built to answer, and it does: our rasteriser draws Segoe UI at 11 to 28 pixels more evenly than Windows' greyscale rendering and close to ClearType, a little lighter at 11 and 12 pixels. What is left is tuning (a slight darkening of thin strokes) and the rule for scaled displays. The fallback of letting Windows rasterise the glyphs is unlikely to be needed.
  • OpenGL is weakest where desktop apps often run. Over Remote Desktop, in virtual machines and on old integrated graphics, OpenGL 3.3 can be missing or slow, and there is no automatic software fallback as there is for Windows' own drawing. If that turns out to matter, the remedy is shipping a software OpenGL (Mesa) or a translation layer (ANGLE) beside the program.
  • "Same names" is not "same behaviour". Text metrics, font fallback and antialiasing will differ from Java2D, so layouts will be a pixel or two different from the Kotlin app.
  • Threads reach into the centre of the VM. Splitting execution state from the heap touches the interpreter loop, the collector, error handling and every native that keeps temporaries. Races in the runtime itself are hard to find: ThreadSanitizer does not run on Windows, so the safeguards are the single lock around all script-visible state and a stress mode that switches threads at every safe point.
  • A flow cannot pause inside a C++ function. If forEach, map or sort is native and calls back into WinterWolf, a suspending call made from that callback has a C++ frame in its way. Kotlin allows it there, and Snips will do it. So the collection functions that take a lambda are written in WinterWolf or expanded in place, and what remains native reports a clear error instead of misbehaving.
  • App logic outside the UI is only partly covered. Threads, processes and sockets (5.5) give the apps what their background work needs. JadeMem's kernel-memory queries through native calls, JadeGen's 3D rendering and Snips' evaluator are still theirs to port.
  • No IME. JadeUI has no input-method composition in either backend; the port inherits that unless it is added natively.
